# TPL-001 — 작업 문서 양식 (초안)

> **문서 지위: TPL-001 / Notion 협업 작업 페이지 양식 / 초안 v0.2 (2026-10-08) / 미승인·논의용**
> 본문은 검토 초안이며 현행 GOV-001·PROC-001을 개정하거나 새로운 의무를 즉시 발생시키지 않는다.

관련 절차: [PROC-001 — 지시 문서 작성 운영 규칙](../proc/PROC-001.md)
공통 원칙: [GOV-001 — 협업 운영 규칙](../gov/GOV-001.md)

## 제1조(목적·적용 범위·협업 작성 환경 및 타 규정과의 관계)

① **목적:** 이 문서(TPL-001)는 사용자와 설계 AI가 Notion에서 작업 내용을 공동으로 작성·논의·검토·수정하는 협업 작업 페이지의 구성과 표기 형식을 정하는 것을 목적으로 한다. 협업 작업 페이지는 작업 항목과 결정 상태, 논의 경과 및 변경 내용을 식별·추적하고, 가안 문서와 정식 문서의 버전을 구분하여 관리하는 공간으로 사용한다.

② **적용 범위:** 이 문서는 PROC-001에 따른 협업 작업 페이지의 작업 항목 구성, 상태 표기와 색상, 작업 기록, 변경 대장 및 가안·정식 문서의 버전 관리 형식에 적용한다. 작업 대상은 프로젝트 전체뿐 아니라 논문의 특정 장, 게임의 개별 오브젝트, 코드의 특정 기능 등 사용자가 지정한 개별 작업 단위를 포함한다. 이 문서는 협업 작업 페이지의 양식이며, 실행 AI에게 전달하는 최종 실행 지시서 자체의 출력 양식으로 적용하지 않는다.

③ **협업 작성 환경:** 사용자와 설계 AI는 하나의 Notion 협업 작업 페이지를 공동 작성·논의의 기준 공간으로 사용한다. 작업 내용, 결정 상태, 작업 기록, 변경 대장 및 문서 버전 사이의 관계를 사용자가 확인하고 추적할 수 있도록 구성하며, 상태 색상·토글·콜아웃·페이지 멘션 등 Notion의 편집·표시 기능을 활용할 수 있다. 협업 작업 페이지에는 미결·논의 중·검증 필요 사항과 확정된 내용을 구분하여 기록할 수 있으며, 페이지의 기재 내용이나 정식 문서로의 승격만으로 실제 작업의 실행이 승인된 것으로 보지 않는다.

④ **타 규정과의 관계:** GOV-001은 공통 원칙을, PROC-001은 논의·승인·상태 변경·검증·컴파일·이관 및 실행에 관한 절차를 정하며, 이 문서(TPL-001)는 그 절차에 사용하는 Notion 협업 작업 페이지의 형식을 정한다. 실행 AI에게 전달하는 최종 Markdown(`.md`) 실행 지시서의 구성·형식·출력 규격은 별도 신설 예정인 TPL-002에서 정한다. 협업 작업 페이지의 내용을 최종 실행 지시서로 정리·전달할 때에는 PROC-001의 해당 요건을 따르며, 협업 기록과 실행 지시를 구분한다. 이 문서의 형식 규정은 GOV-001 및 PROC-001의 승인·검증·중단 요건을 변경하거나 대신하지 않는다.

## 제2조(작성 언어·페이지 형식 및 식별)

① **작성 언어:** 협업 작업 페이지는 한국어로 작성한다. 널리 통용되는 한국어 기술 용어는 한국어 표기만 사용할 수 있으며, 그렇지 않은 기술 용어는 처음 등장하는 위치에서 한국어 표현과 원어를 병기하고 이후에는 의미가 명확한 경우 한국어 표현만 사용할 수 있다. 통용 여부의 판단이 어려우면 병기한다.

② **원문 유지:** 다음 각 호는 번역하거나 바꾸어 쓰지 않고 원문 그대로 표기한다.

1. 파일명·폴더명·경로
2. 원본 자료의 시트명·열 이름·제목·식별자(ID) 등 실행 AI가 원본과 대조해야 하는 명칭
3. 코드·명령어·함수명·변수명·수식
4. 원문 인용

③ **페이지 형식:** 협업 작업 공간은 Notion 페이지로 작성한다. 페이지의 구성과 표기는 사용자가 작업 내용·결정 상태·논의 경과 및 변경 내용을 쉽게 읽고 확인할 수 있도록 한다.

④ **페이지명:** 협업 작업 페이지의 이름은 `작업공간_`으로 시작하고, 그 뒤에 작업 목표와 문서 버전을 밑줄(`_`)로 구분하여 붙인다. 페이지명에는 공백과 대괄호 등 특수문자를 사용하지 않는다. 예: `작업공간_논문2장작성_v1.0`. 버전 부여 및 확정 기준은 제6조에 따른다.

⑤ **산출물과의 구분:** 협업 작업 페이지의 형식은 해당 작업에서 생성되는 실제 작업 산출물의 파일 형식과 구분한다. 작업 산출물별 종류·수량·형식 등은 협업 작업 페이지에서 논의·정리하며, 최종 실행 지시서에는 PROC-001 제8조제1항제2호에 따라 명시한다.

⑥ **Notion 표시 형식:** 협업 작업 페이지는 사용자가 내용을 쉽게 알아보고 확인할 수 있도록 다음 각 호에 따라 작성한다.

1. 표는 Notion의 표 기능을 사용하여 읽기 쉬운 형태로 작성한다.
2. 상태 색상·토글·콜아웃·페이지 멘션 등 Notion의 편집·표시 기능을 활용할 수 있으며, 같은 종류의 정보에는 일관된 형식을 적용한다.
3. 도구별 실행 방식이 필요한 경우에는 본문과 분리된 부록에 둔다.

## 제3조(문서 머리말)

① **문서 제목:** 지시 문서의 첫 줄에는 Markdown 최상위 제목(`#`)으로 작업 지시서의 제목을 기재한다. 제목은 작업 대상을 구체적으로 식별할 수 있도록 작성한다.

② **머리말 표:** 제목 다음에는 Markdown 표 문법을 사용한 2열 표를 배치한다. 첫 번째 열에는 항목명을, 두 번째 열에는 해당 값을 기재하며, 다음 각 호의 항목을 순서대로 배치한다.

1. **문서 버전:** 해당 지시 문서의 버전. 구체적인 부여 기준은 별도 조항에서 정한다.
2. **문서 상태:** 지시 문서 자체의 작성·승인 상태. 개별 쟁점의 결정 상태와 구분한다.
3. **작업 목적:** 이번 지시를 통해 달성하려는 핵심 목표를 간결하게 기술한다.
4. **작업 범위:** 이번 지시의 적용 대상 및 제외되는 범위를 요약한다.

③ **선택 항목:** 작성 기준일과 문서 식별자는 필요한 경우 표에 추가할 수 있다. 작성 기준일을 추가할 때에는 문서 상태 다음, 작업 목적 앞에 배치한다. 문서 식별자의 배치 위치는 별도 합의가 없으면 문서 버전 앞에 둔다.

④ **작성 원칙:** 머리말에는 작업 식별과 개요 파악에 필요한 정보만 기재한다. 산출물 상세 명세·변경 지시·검증 기준 등은 본문에 두며, 머리말과 본문의 목적·범위·상태가 서로 일치해야 한다.

⑤ **Markdown 형식:** 머리말은 제2조제6항의 플랫폼 독립 Markdown 원칙을 따르며, 제목과 2열 표 외에 Notion 전용 블록·HTML 태그를 사용하지 않는다. 표의 내용이 길면 셀 안에서 줄바꿈을 강제하지 않고 간결한 문장으로 정리한다.

⑥ **표준 작성 예시:** 다음 예시의 제목 수준·열 구성·항목명·순서를 기본 양식으로 사용한다. 대괄호 안의 값은 실제 작업 내용으로 바꾸며 선택 항목은 필요하지 않으면 행 자체를 생략한다.

```markdown
# [작업명] 작업 지시서

| 항목 | 내용 |
| --- | --- |
| 문서 버전 | v1.0 |
| 문서 상태 | 최종 승인 |
| 작성 기준일 | 2026-10-08 |
| 작업 목적 | 논문 제2장의 이론적 배경과 선행연구 서술 개선 |
| 작업 범위 | 제2장 본문과 관련 인용·참고문헌 정합성 검토 및 수정. 다른 장의 본문 수정은 제외 |
```

## 제4조(본문의 기본 절 구성)

① **구성 원칙:** 최종 작업 지시 문서의 본문은 실행 AI가 작업을 수행하고 검증하는 데 필요한 정보로 구성한다. PROC-001의 논의 경과·대안 비교·미승인 제안은 원칙적으로 실행 지시 본문에 수록하지 않는다. 다만 정확한 수행이나 재발 방지에 필요한 결정 근거·제약·검증 조건은 남긴다.

② **표준 절:** 본문은 다음 각 호의 절로 구성한다. 세부 항목의 수와 깊이는 작업 단위에 맞추되 PROC-001 제8조제1항의 필수 지시 사항은 빠짐없이 반영하며, 각 사항의 반영 위치는 부록 ○의 대응표에 따른다.

1. **작업 목적·대상 및 입력 자료:** 작업의 목적, 원본의 파일명·버전·위치 또는 식별 방법, 참조 자료, 작업 대상과 적용 위치, 착수 전 확인 사항 및 불일치 시 중단 조건을 기술한다.
2. **산출물 명세:** 산출물별 종류·개수·내용 범위·파일 형식·파일명 또는 명명 규칙·저장 및 제공 위치·필수 구성·수용 기준을 명시한다. 원본 보존·덮어쓰기 여부 및 개수가 달라지는 조건도 기술한다.
3. **작업 수행 명세:** 실제 수행할 작업을 계층형 항목으로 구분하고 각 항목에 적용할 수정·생성 명령, 필요한 근거, 보존·금지 조건, 검증·완료 기준, 예외 시 중단·보고 방법을 함께 기술한다. 작업 전체에 공통인 실행·검증·보고 조건은 제3절의 마지막 하위 절에 배치하고, 앞선 작업 항목에서 참조할 수 있다. 작업 완료 후 완료·부분 완료·미적용·실패의 구분, 근거, 실제 수정 위치 및 남은 문제를 보고하는 형식을 이 절의 공통 항목에 둔다. PROC-001 제8조제1항제9호의 실행 AI 준수 원칙도 누락하지 않는다.
4. **지시 문서 변경 이력:** 지시 문서 자체의 버전별 주요 변경 대상·변경 내용·이유를 표로 정리한다. 삭제·폐기한 지시가 다시 도입되는 것을 방지할 필요가 있으면 제외 이유와 현재 적용 범위를 식별할 수 있도록 한다.
5. **실행 제외 항목(선택):** PROC-001 제9조제2항에 따라 참고로 전달하는 미결·보류·검증 필요 사항을 둔다. 이 절의 내용은 실행 명령이 아니며, 실행 AI는 이를 수행하지 않는다.

③ **작업 수행 명세의 계층:** 제3절은 `3.1`부터 `3.n-1`까지를 개별 작업 항목으로 구성하고, 마지막 `3.n`을 **공통 실행·검증·보고 조건** 절로 둔다. `n`은 실제 하위 절 수에 따라 정하며 고정 번호 `3.2`를 강제하지 않는다. `3.1`, `3.1.1` 등 숫자 계층으로 식별하는 단위를 **작업 항목**이라 한다. 작업 항목은 필요에 따라 `3.1.1`까지 세분할 수 있다. 그보다 세밀한 내용을 나눌 필요가 있을 때 사용하는 `(1)`, `(2)`, `(3)` 등의 괄호 번호는 **세부 구분**이라 하며, 작업 항목으로 간주하지 않는다. 세부 구분은 필요한 경우에만 사용한다. 상위 항목은 작업 대상과 목표를, 하위 항목은 실제 수행 내용을 구체화한다. 각 항목에 필요한 근거는 원본과 대조 가능한 식별자 또는 출처로 연결하며, 불필요한 근거나 반복 설명은 생략한다.

④ **결정 상태의 처리 및 색상:** PROC-001에 따른 논의 중에는 `3.1`, `3.1.1` 등 모든 계층의 **작업 항목** 제목 끝에 결정 상태를 표시한다. `(1)`, `(2)` 등의 **세부 구분**에는 별도의 결정 상태를 붙이지 않으며, 해당 내용은 소속 작업 항목의 상태를 따른다. Notion에서 공동 작성하는 동안 상태 표기의 **글자색**은 다음 각 호와 같이 구분한다.

1. **\[제기\]:** 빨간색 — Notion 색상 `red`
2. **\[논의 중\]:** 노란색 — Notion 색상 `yellow`
3. **\[확정\]:** 초록색 — Notion 색상 `green`
4. **\[삭제 확정\]:** 보라색 — Notion 색상 `purple`
5. **\[선행 결정 대기\]:** 파란색 — Notion 색상 `blue`
6. **\[검증 필요\]:** 주황색 — Notion 색상 `orange`. 결정 상태에 덧붙이는 검증 플래그로서 `[확정][검증 필요]`와 같이 표기하며, 별도의 결정 상태로 간주하지 않는다.

Notion의 편집용 색상 표기는 해당 상태 텍스트에만 적용하며, Notion의 Markdown 표현에서는 예를 들어 `<span color="red">[제기]</span>`처럼 지정할 수 있다. 이는 **Notion 편집 환경에서의 시각적 표기 방식**일 뿐, 최종 플랫폼 독립 Markdown 파일에는 색상 지정 태그를 출력하지 않고 상태 텍스트만 유지한다. 최종 실행 지시 문서의 수행 명세에는 승인되고 사전 검증이 완료되어 실행 대상으로 확정된 내용만 남긴다. `[삭제 확정]`은 기존 작업물의 실제 삭제가 승인된 경우에만 삭제 명령으로 작성한다.

⑤ **변경 이력 표의 형식:** 제2항제4호는 Markdown 표로 작성하며 기본 열은 `버전 | 일자 | 변경 대상 | 변경 내용 | 변경 이유 | 승인`으로 한다. 변경 이유에는 필요 시 폐기·제외의 범위와 재도입을 경계해야 하는 조건을 명시한다. 변경 이력은 현행 지시를 이해하기 위한 참고 정보이며, 과거 지시를 실행하거나 복원하는 근거로 사용하지 않는다. 단순 오탈자 등 실행 판단에 영향이 없는 수정은 간략히 기록할 수 있다.

⑥ **정합성과 우선순위:** 제3절의 현행 실행 명령과 제4절의 변경 이력이 상충하면 해당 항목을 임의로 해석하거나 수행하지 않고 상충 사항을 보고한다. 변경 이력으로 현행 본문의 승인 범위를 확대·축소하지 않는다. 버전의 부여 및 확정 기준은 제6조에 따른다.

## 제5조(절·항목 및 표기)

① **제목 계층:** 문서의 제목과 본문 절은 Markdown 제목 문법을 사용하며, 문서 제목은 `#`, 본문 주요 절은 `##`, 제4조의 작업 항목 `3.1` 등은 `###`, 그 하위 작업 항목 `3.1.1` 등은 `####`로 표시한다. 제목 계층은 문서 구조를 나타내는 서식이며, 작업 항목 번호는 해당 작업을 식별하는 번호로서 서로 구분한다.

② **목록 및 표:** 지시의 실행 순서와 선후 관계가 중요할 때는 번호 목록을 사용하고, 병렬 조건·참고 정보·비교 정보에는 글머리표 또는 표를 사용할 수 있다. 제4조제3항의 `(1)`, `(2)` 등 세부 구분은 별도의 Markdown 제목 계층을 만들지 않는다.

③ **식별자 표기:** 변경 ID·파일 위치·함수명·식 번호 등 추적에 필요한 식별자는 원문과 일치하도록 기재하며, 제2조제2항의 원문 유지 원칙을 따른다.

④ **표기 일관성:** 동일한 종류의 정보에는 문서 전체에서 일관된 표기 방식을 사용한다. 표·목록·제목 계층을 조정하더라도 작업 항목의 식별 번호와 참조 관계가 불명확해지지 않도록 한다.

## 제6조(지시 문서의 변경 및 버전 관리)

① **관리 대상의 구분:** 지시 문서 작성 과정의 쟁점·결정·변경은 PROC-001 제6조의 작업 기록과 변경 대장에 따라 추적한다. 최종 지시 문서의 제4절 '지시 문서 변경 이력'은 그 기록 중 실행 AI가 현행 지시를 이해하고 폐기된 요구사항의 재도입을 방지하는 데 필요한 변경만 요약하여 전달한다. 두 기록은 목적이 다르며 동일한 내용을 중복해서 전부 수록하지 않는다.

② **변경 기록 및 승인 추적:** 변경 관리에서는 다음 각 호를 따른다.

1. PROC-001의 변경 대장에는 변경 ID, 대상, 수정 내용, 결정 상태, 승인 기록 또는 참조를 기본으로 두고, 필요한 경우 현행 내용, 이유·근거, 연쇄 영향 및 검증 조건을 연결한다.
2. 변경 대상이 다른 작업 항목·정의·참조·검증 기준에 영향을 미치면 PROC-001 제7조에 따라 연쇄 영향을 점검한다. 기존 기록의 ID·위치·링크를 활용하여 불필요한 중복 작성을 피한다.
3. 승인되지 않은 변경안과 승인된 실행 항목을 구분하고, 사용자의 승인 및 PROC-001 제4조의 상태 변경 요건을 충족하지 않은 내용을 임의로 확정하지 않는다.

③ **버전 상승 및 수정 수준:** 개별 편집이나 작업 항목의 상태 변경만으로 버전을 자동 상승시키지 않는다. 사용자가 현재 변경의 기록이나 하루 작업의 마무리를 위하여 버전 상승을 요청하는 경우, 사용자와 AI가 수정 수준을 명시적으로 합의한 뒤 다음 각 호의 기준에 따라 한 단계만 상승시킨다.

1. **Major 수정:** 버전 번호의 첫째 자리 정수를 1 증가시키는 수정으로 한다.
2. **Minor 수정:** 버전 번호의 점 뒤 정수를 1 증가시키는 수정으로 한다.
3. **수정 수준의 결정:** 변경의 양·중요도에 관계없이 사용자와 AI의 명시적 합의로 Major 또는 Minor를 정한다. 변경량에 따른 자동 분류나 한 번에 2 이상 증가시키는 변경은 허용하지 않는다.
4. **기록:** 버전 상승 시 변경 대상·내용·이유·일자 및 승인 기록을 제5항의 변경 이력에 반영한다.

버전 상승은 당시의 문서 상태를 식별·보존하기 위한 행위이며, 미결 항목의 확정이나 PROC-001의 컴파일·이관·실행 승인을 의미하지 않는다.

④ **가안 문서와 정식 문서의 구분:** 버전 식별과 단계 승격은 다음 각 호에 따른다.

1. **가안 문서:** 사용자의 요청에 따라 AI가 우선 작성한 초안으로서 `v0.1`부터 시작한다. 이후 수정 버전도 첫째 자리 `0`을 유지하며, 일반적인 버전 상승으로 `v1.0` 이상의 정식 문서가 될 수 없다.
2. **정식 문서:** 사용자의 의견을 반영한 뒤 사용자가 명시적으로 정식 문서로의 승격을 선언한 경우에만 해당 문서를 정식 문서로 취급한다. 승격 시 직전 가안의 버전 번호와 관계없이 `v1.0`을 부여한다(예: `v0.99 → v1.0`). 이 승격은 제3항의 통상적인 Major/Minor 수정과 구분한다.
3. **승격과 실행 승인:** 정식 문서로의 승격은 PROC-001의 논의 종결·컴파일·이관 요건을 대신하지 않으며, 그 자체로 실제 작업 실행을 허용하지 않는다.
4. **이력 보존:** 버전이 변경되거나 문서가 승격될 때에는 이전 버전과 변경·승격 내역을 식별할 수 있도록 보존한다. 미승인 상태의 내용을 승인된 실행 지시로 표시하지 않는다.
5. **번호 해석:** 버전 번호는 첫째 자리와 점 뒤 자리의 정수로 구분해 관리하며, 점 뒤 자릿수를 소수값처럼 해석하지 않는다. Major 수정 시 첫째 자리 정수를 1 증가시키고 기존 Minor 번호는 `0`으로 초기화한다(예: `v1.4 → v2.0`). 가안 문서는 정식 문서 승격 전까지 첫째 자리 `0`을 유지하며, 일반적인 Major 상승을 적용하지 않는다.

⑤ **최종 변경 이력의 작성:** 제4조제2항제4호와 제4조제5항에 따라 `버전 | 일자 | 변경 대상 | 변경 내용 | 변경 이유 | 승인` 형식의 Markdown 표로 작성한다. '변경 대상'은 가능한 한 작업 항목 번호 또는 식별자로 연결하고, '승인'에는 사용자 승인 기록 또는 확인 가능한 참조를 기재한다. 폐기·삭제의 이유 및 현재 제외 범위는 실행 판단에 영향을 줄 때 명시한다.

⑥ **실행 명령과의 분리:** 변경 이력은 현행 지시를 이해하기 위한 참고 정보이며, 과거안을 복원하거나 실행할 권한을 부여하지 않는다. 현행 지시와 변경 이력 사이에 해소되지 않은 상충이 발견되면 PROC-001과 GOV-001의 중단·보고 원칙에 따라 처리한다.

## 제7조(문체 및 명령의 명확성)

① **명령형 작성:** 실행 지시는 명령형으로 작성하며, 다음 각 호의 기준을 따른다.

1. 실행 AI가 수행할 행동을 명확한 동사로 표현한다.
2. 명령에는 작업 대상, 수행 행동 및 요구 결과를 식별할 수 있도록 한다.
3. 완료 여부를 판단해야 하는 경우 구체적인 완료 조건 또는 검증 기준을 제시한다.
4. '적절히', '가능한 한', '필요에 따라' 등 해석의 여지가 있는 표현에는 적용 조건이나 판단 기준을 명시한다.

② **불확실한 정보의 처리:** 사실·가정·미결 사항과 실행 명령을 구분하며, 다음 각 호를 따른다.

1. 확인되지 않은 사실을 확정된 사실처럼 서술하지 않는다.
2. 작업 수행에 필요한 가정은 그 내용과 적용 조건을 명시하되, 가정만으로 미승인 작업의 실행을 허용하지 않는다.
3. 미승인·미결·사전 검증 필요 항목을 실행 명령으로 변환하지 않으며, PROC-001 제8조제3항에 따라 실행 대상에서 제외한다.
4. 실행에 영향을 미치는 불확실성이나 상충이 해소되지 않은 경우 해당 항목의 실행을 보류하고 이유·영향 범위·필요한 확인 사항을 보고하도록 명시한다.

③ **명령 동사와 권한의 구분:** 실행 AI가 수행할 행동과 허용 범위를 구별할 수 있도록 다음 각 호의 용어를 사용한다.

1. **검토:** 지정된 대상의 현황·문제·적합성을 살펴 판단 결과를 제시하는 행위. 검토 지시만으로 원본의 변경·삭제를 허용하지 않는다.
2. **수정:** 지정된 대상을 승인된 범위와 조건에 따라 변경하는 행위. 수정 지시만으로 대상 밖의 파일·절·기능 변경이나 원본 덮어쓰기를 허용하지 않는다.
3. **검증:** 결과가 지정된 요구사항과 판정 기준을 충족하는지 확인하는 행위. 검증 지시만으로 기준·임계값·대상·절차를 변경·완화·생략하거나 결과를 조작할 수 없다.
4. **보고:** 수행 상태, 근거, 실제 수정 위치 및 남은 문제를 정해진 형식으로 전달하는 행위. 보고 지시만으로 후속 수정이나 미승인 작업의 실행을 허용하지 않는다.

④ **근거 및 설명:** 실행에 필요한 근거와 설명만 포함하며, 다음 각 호를 따른다.

1. PROC-001에서 이루어진 대화·대안 비교·논의 경과를 원칙적으로 그대로 옮기지 않는다.
2. 작업 방법·요구사항·제약 조건의 이해에 필요한 이유는 간결하게 기술한다.
3. 근거 자료는 실행 AI가 확인할 수 있도록 출처·식별자·위치를 명시한다.
4. 폐기된 제안과 그 이유는 현재 작업의 해석 또는 재도입 방지에 필요한 경우 제4조의 지시 문서 변경 이력에 기록하고, 현행 실행 명령과 혼합하지 않는다.

## 제8조(전달 대상 및 전달 단위)

① 주된 전달 대상은 GPT·Claude 등 **기존 대화 이력을 공유하지 않는 별도 실행 AI**를 원칙으로 한다.

② 전달 단위는 최종 지시 문서 및 실행에 필요한 원본·참조 자료, 승인·제외 범위와 검증·보고 요구사항으로 한다.

③ 전달 매체(Notion 링크, 파일 첨부, 저장소 경로 등)는 실제 접근 권한과 자료 재현 가능성을 확인하여 결정한다.

④ 지시 문서의 작성·승인·전달은 실제 파일 수정이나 작업 실행의 자동 승인을 뜻하지 않는다.

## 제9조(양식 점검 및 예외)

① 컴파일 완료 전 파일 형식, 머리말, 필수 절, 식별자, 산출물 명세, 접근 가능한 입력 자료, 지시의 독립 이해 가능성을 확인한다.

② 형식상의 편의를 이유로 GOV-001 및 PROC-001의 승인·검증·중단 요건을 완화하지 않는다.

③ 특수한 형식이 필요한 경우 예외의 필요성·적용 범위·호환성·승인 여부를 명시하고 별도로 논의한다.

다음은 제3조와 제4조에 따른 출력 예시이다. 대괄호의 설명은 실제 값으로 대체하며, 선택 항목과 해당하지 않는 예시는 생략한다. 실행 가능한 항목만 최종 지시의 제3절에 포함한다.

```markdown
# [작업명] 작업 지시서

| 항목 | 내용 |
| --- | --- |
| 문서 버전 | [버전] |
| 문서 상태 | [최종 승인 등 실제 상태] |
| 작업 목적 | [핵심 목표] |
| 작업 범위 | [적용 대상 및 제외 범위] |

## 1. 작업 목적·대상 및 입력 자료
- 작업 목적: [수행할 작업의 목표]
- 원본: [파일명·버전·위치 또는 식별 방법]
```

## 부록 C. 제정 이력

- **초안 v0.1 — 2026-10-08:** PROC-001에서 생성하는 최종 지시 문서에 범위를 한정하여 출력 형식·절 구성·문체·전달 규격의 최초 검토안 작성. 승인 전 문서임.
- **초안 v0.2 — 2026-10-08 (Minor: v0.1 → v0.2):** 제1조를 Notion 협업 작업 페이지의 목적·적용 범위·협업 작성 환경·타 규정과의 관계로 개정하여, PROC-001의 절차 및 TPL-002의 최종 Markdown(`.md`) 실행 지시서 양식과 역할을 구분함. 제2조를 사용자가 읽고 확인하기 쉬운 Notion 페이지 형식으로 개정하고, 페이지명 규칙을 `작업공간_작업목표_버전`으로 변경함. 한국어 작성·기술 용어 병기·원문 유지 규칙은 유지하고, Notion 표시 기능을 활용하도록 정리함. 변경 이유: 협업 작업 페이지와 최종 실행 지시서의 양식을 분리하고 오늘의 수정 상태를 기록하기 위함. 승인 기록: 사용자의 당일 마무리 및 부록 C 이력 추가 요청과 'Minor: v0.1 → v0.2' 선택에 따름. 이번 버전 상승은 정식 문서 승격이나 실행 승인을 의미하지 않음. 제3조 이하 및 부록의 내용 정합성은 후속 검토 대상으로 남김.

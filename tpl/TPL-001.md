## 제1조(목적·적용 범위·협업 작성 환경 및 타 규칙과의 관계)

① **목적:** 이 문서(TPL-001)는 사용자와 설계 AI가 Notion에서 작업 내용을 공동으로 작성·논의·검토·수정하는 협업 작업 페이지의 구성과 표기 형식을 정하는 것을 목적으로 한다. 협업 작업 페이지는 작업 항목과 결정 상태, 논의 경과 및 변경 내용을 식별·추적하고, 개별 작업의 승인 기록과 변경 대장을 유지하는 공간으로 사용한다. 협업 작업 페이지에는 문서 버전을 부여하거나 갱신하지 않고 가안·정식 지위를 구분하지 않는다.

② **적용 범위:** 이 문서는 PROC-001에 따른 협업 작업 페이지의 작업 항목 구성, 상태 표기와 색상, 작업 기록, 변경 대장 및 협업 작업 페이지의 변경·기록 관리 형식에 적용한다. 작업 대상은 프로젝트 전체뿐 아니라 논문의 특정 장, 게임의 개별 오브젝트, 코드의 특정 기능 등 사용자가 지정한 개별 작업 단위를 포함한다. 이 문서는 협업 작업 페이지의 양식이며, 실행 AI에게 전달하는 실행 지시 문서 자체의 출력 양식으로 적용하지 않는다.

③ **협업 작성 환경:** 사용자와 설계 AI는 하나의 Notion 협업 작업 페이지를 공동 작성·논의의 기준 공간으로 사용한다. 작업 내용, 결정 상태, 작업 기록, 변경 대장 및 변경 이력 사이의 관계를 사용자가 확인하고 추적할 수 있도록 구성하며, 상태 색상·토글·콜아웃·페이지 멘션 등 Notion의 편집·표시 기능을 활용할 수 있다. 협업 작업 페이지에는 미결·논의 중·검증 필요 사항과 확정된 내용을 구분하여 기록할 수 있으며, 페이지의 작성·기재·전달만으로 실제 작업의 실행이 승인된 것으로 보지 않는다.

④ **타 규칙과의 관계:** GOV-001은 공통 원칙을, PROC-001은 논의·승인·상태 변경·검증·컴파일·이관 및 실행에 관한 절차를 정하며, 이 문서(TPL-001)는 그 절차에 사용하는 Notion 협업 작업 페이지의 형식을 정한다. 실행 AI에게 전달하는 Markdown(`.md`) 실행 지시 문서의 구성·형식·출력 규격은 별도 신설 예정인 TPL-002에서 정한다. 협업 작업 페이지의 내용을 실행 지시 문서로 정리·전달할 때에는 PROC-001의 해당 요건을 따르며, 협업 기록과 실행 지시를 구분한다. 이 문서의 형식 규칙은 GOV-001 및 PROC-001의 승인·검증·중단 요건을 변경하거나 대신하지 않는다.

## 제2조(작성 언어·페이지 형식 및 식별)

① **작성 언어:** 협업 작업 페이지는 한국어로 작성한다. 널리 통용되는 한국어 기술 용어는 한국어 표기만 사용할 수 있으며, 그렇지 않은 기술 용어는 처음 등장하는 위치에서 한국어 표현과 원어를 병기하고 이후에는 의미가 명확한 경우 한국어 표현만 사용할 수 있다. 통용 여부의 판단이 어려우면 병기한다.

② **원문 유지:** 다음 각 호는 번역하거나 바꾸어 쓰지 않고 원문 그대로 표기한다.

1. 파일명·폴더명·경로
2. 원본 자료의 시트명·열 이름·제목·식별자(ID) 등 실행 AI가 원본과 대조해야 하는 명칭
3. 코드·명령어·함수명·변수명·수식
4. 원문 인용

③ **페이지 형식:** 협업 작업 공간은 Notion 페이지로 작성한다. 페이지의 구성과 표기는 사용자가 작업 내용·결정 상태·논의 경과 및 변경 내용을 쉽게 읽고 확인할 수 있도록 한다.

④ **페이지명:** 협업 작업 페이지의 이름은 `작업공간_작업목표_YYYYMMDD`로 한다. 날짜는 최초 작성일이며 이후 편집해도 바꾸지 않는다. 페이지명에는 공백과 대괄호 등 특수문자를 사용하지 않는다. 예: `작업공간_논문2장작성_20261008`. 같은 목표·같은 날짜의 페이지는 고유 페이지 ID·URL로 구분할 수 있으며 의무적인 번호·시각 접미사나 매번 새 페이지를 만드는 의무를 두지 않는다. 후속 페이지가 기존 작업을 잇는 경우 기존 페이지·CHG-ID·승인 기록을 연결한다. 식별·기록 기준은 제6조에 따른다.

⑤ **산출물과의 구분:** 협업 작업 페이지의 형식은 해당 작업에서 생성되는 실제 작업 산출물의 파일 형식과 구분한다. 작업 산출물별 종류·수량·형식 등은 협업 작업 페이지에서 논의·정리하며, 실행 지시 문서에는 PROC-001 제8조제1항제2호에 따라 명시한다. 산출물의 파일명은 대상과 용도, 필요한 경우 버전을 식별할 수 있도록 정하며, 이 양식에서 고정된 파일명 규칙을 일률적으로 요구하지 않는다.

⑥ **Notion 표시 형식:** 협업 작업 페이지는 사용자가 내용을 쉽게 알아보고 확인할 수 있도록 다음 각 호에 따라 작성한다.

1. 표는 Notion의 표 기능을 사용하여 읽기 쉬운 형태로 작성한다.
2. 상태 색상·토글·콜아웃·페이지 멘션 등 Notion의 편집·표시 기능을 활용할 수 있으며, 같은 종류의 정보에는 일관된 형식을 적용한다.
3. 도구별 실행 방식이 필요한 경우에는 본문과 분리된 부록에 둔다.

⑦ **향후 규칙의 명칭:** 앞으로 작성하는 규칙은 공식 명칭에 ‘규칙’을 사용하고, 페이지 제목과 머리말 등에 같은 명칭을 일관되게 기재한다. 과거 규칙과 기록의 ‘규정’·‘규칙’ 불일치는 이 명칭 통일을 이유로 소급 수정하지 않는다.

## 제3조(페이지 머리말)

① **페이지 제목:** 협업 작업 페이지의 제목은 작업 대상을 구체적으로 식별할 수 있도록 작성하며, 페이지명은 제2조제4항에 따른다.

② **머리말 표:** 페이지 제목 다음에는 2열 표를 배치한다. 첫 번째 열에는 항목명을, 두 번째 열에는 해당 값을 기재하며, 다음 각 호의 항목은 필수로 포함하고 아래 순서대로 배치한다.

1. **작성 기준일:** 해당 협업 작업 페이지의 최초 작성일로서 제목 날짜와 일치하며 이후 편집해도 바꾸지 않는다.
2. **작업 목적:** 이번 작업을 통해 달성하려는 핵심 목표를 간결하게 기술한다.
3. **작업 범위:** 이번 작업의 적용 대상 및 제외되는 범위를 요약한다.

③ **선택 항목:** 문서 식별자는 선택 정보로 유지하며 필요한 경우 작성 기준일 앞에 둔다. 협업 작업 페이지 머리말에는 문서 버전·문서 상태 행을 두지 않는다.

④ **작성 원칙:** 머리말에는 작업 식별과 개요 파악에 필요한 정보만 기재한다. 산출물 상세 명세·변경 내용·검증 기준 등은 본문에 두며, 머리말과 본문의 목적·범위·상태가 서로 일치해야 한다.

⑤ **Notion 표 형식:** 머리말 표는 Notion의 표 기능을 이용하여 2열 표로 작성한다. 표는 페이지의 사용 가능한 너비를 충분히 활용하며, ‘항목’ 열은 항목명을 읽을 수 있는 최소한의 너비로 두고 ‘내용’ 열에는 나머지 너비를 최대한 배정한다. 내용이 가능한 한 한 줄로 표시되도록 ‘내용’ 열의 너비를 넉넉하게 확보한다. 셀 안에서 줄바꿈을 강제하지 않으며, 표시 공간을 넘는 내용은 의미를 유지하면서 간결한 문장으로 정리한다.

⑥ **표준 작성 예시:** 페이지 머리말의 표준 작성 예시는 부록 D에 둔다.

## 제4조(본문의 기본 절 구성)

① **구성 원칙:** 협업 작업 페이지의 본문은 사용자가 작업 내용과 목적, 결정 상태, 논의 경과 및 진행 현황을 이해하고 판단할 수 있는 정보로 구성한다. 확정된 내용뿐 아니라 논의 경과·대안 비교·미승인 제안·미결 사항도 서로 구분하여 기록할 수 있다. 상세 내용은 필요한 위치에 연결하고, 현재 판단에 필요한 근거·제약·확인 기준은 본문에서 쉽게 확인할 수 있도록 한다.

② **표준 절:** 본문은 다음 각 호의 절로 구성한다.

1. **작업 목적·대상 및 입력 자료:** 작업의 목적, 원본의 파일명·버전·위치 또는 식별 방법, 참조 자료, 작업 대상과 적용 위치, 착수 전 확인 사항 및 불일치 시 중단 조건을 기술한다. 입력 자료와 참조 자료는 식별 정보와 기준 버전 또는 확인 시점을 기록하고, 확인한 자료·범위와 미확인 후보를 구분한다. 미확인 후보에는 확인하지 못한 이유와 작업 판단에 미치는 영향을 적는다. 알려진 관련 저장소·사본 등의 자료도 해당 작업에 영향을 주는 경우 참조 후보로 식별한다.
2. **산출물 명세:** 산출물별 종류·개수·내용 범위·파일 형식·파일명 또는 명명 규칙·저장 및 제공 위치·필수 구성·수용 기준을 명시한다. 원본 보존·덮어쓰기 여부 및 개수가 달라지는 조건도 기술한다. 산출물 명세에는 이번 작업이 궁극적으로 목표하는 최종 결과물과 그 설명을 명시한다. 설명은 결과물이 무엇이고 어떤 내용·상태를 갖추어 작업 목적을 달성하는지 알 수 있도록 작성한다. 원본을 제자리에서 수정하는 경우에도 그 수정 결과를 최종 결과물로 식별한다. 작성 과정의 기록이나 실행 지시 문서를 나열하는 것만으로 최종 결과물의 설명을 대신하지 않는다.
3. **작업 수행 명세:** 사용자와 함께 검토할 작업을 계층형 항목으로 구분하고, 각 항목에 작업 대상, 하려는 일, 기대하는 결과, 필요한 근거, 보존·금지 조건 및 완료·확인 기준을 정리한다. 논의할 내용과 확정된 내용은 결정 상태로 구분하며, 불확실성이나 문제가 있으면 이유·영향 범위·필요한 확인 사항을 함께 기록한다. 작업 전체에 공통인 조건과 확인·진행 기록 방식은 제3절의 마지막 하위 절에 두고, 앞선 작업 항목에서 참조할 수 있다. 완료한 내용·확인 결과·실제 반영 위치·남은 작업은 제4절의 변경 대장과 연결하여 사용자가 진행 현황을 확인할 수 있도록 한다. 기존 내용을 변경하는 항목은 수정 위치를 원문에서 확인하고, 확인한 위치와 변경 전후 내용을 식별할 수 있도록 기록한다. 수정할 현행 내용과 보존할 과거 기록을 구분한다. 판단에 영향을 주는 기존 승인·운영 사례가 있으면 확인 위치와 현재 작업에 대한 적용 조건을 연결한다.
4. **변경 대장:** 작업·변경 항목별 결정 상태와 작업 진행 상태, 완료한 내용 및 남은 작업을 Notion 표로 정리한다. 표의 열 구성과 진행 현황 요약 형식은 제5항에 따른다.
5. **협업 작업 페이지 변경 이력:** 협업 작업 페이지 자체의 주요 변경 대상·변경 내용·이유·일자와 사용자 결정·승인 참조를 표로 정리한다. 버전 열은 두지 않는다. 삭제·폐기한 지시가 다시 도입되는 것을 방지할 필요가 있으면 제외 이유와 현재 적용 범위를 식별할 수 있도록 한다.
6. **실행 제외 항목(선택):** PROC-001 제9조제2항에 따라 참고로 전달하는 미결·보류·검증 필요 사항을 둔다. 이 절의 내용은 실행 명령이 아니며, 실행 AI는 이를 수행하지 않는다.

③ **작업 수행 명세의 계층:** 제3절은 `3.1`부터 `3.n-1`까지를 개별 작업 항목으로 구성하고, 마지막 `3.n`을 **공통 작업·확인·기록 조건** 절로 둔다. `n`은 실제 하위 절 수에 따라 정하며 고정 번호 `3.2`를 강제하지 않는다. `3.1`, `3.1.1` 등 숫자 계층으로 식별하는 단위를 **작업 항목**이라 한다. 작업 항목은 필요에 따라 `3.1.1`까지 세분할 수 있다. 그보다 세밀한 내용을 나눌 필요가 있을 때 사용하는 `(1)`, `(2)`, `(3)` 등의 괄호 번호는 **세부 구분**이라 하며, 작업 항목으로 간주하지 않는다. 세부 구분은 필요한 경우에만 사용한다. 상위 항목은 작업 대상과 목표를, 하위 항목은 실제 수행 내용을 구체화한다. 각 항목에 필요한 근거는 원본과 대조 가능한 식별자 또는 출처로 연결하며, 불필요한 근거나 반복 설명은 생략한다.

④ **결정 상태의 처리 및 색상:** PROC-001에 따른 논의 중에는 `3.1`, `3.1.1` 등 모든 계층의 **작업 항목** 제목 끝에 결정 상태를 표시한다. `(1)`, `(2)` 등의 **세부 구분**에는 별도의 결정 상태를 붙이지 않으며, 해당 내용은 소속 작업 항목의 상태를 따른다. Notion에서 공동 작성하는 동안 상태 표기의 **글자색**은 다음 각 호와 같이 구분한다.

1. **[제기]:** 빨간색
2. **[논의 중]:** 노란색
3. **[확정]:** 초록색
4. **[삭제 확정]:** 보라색
5. **[선행 결정 대기]:** 파란색
6. **[검증 필요]:** 주황색. 결정 상태에 덧붙이는 검증 플래그로서 `[확정][검증 필요]`와 같이 표기하며, 별도의 결정 상태로 간주하지 않는다.

상태 색상은 Notion의 글자색 기능을 이용하여 해당 상태 텍스트에만 적용한다. 협업 작업 페이지에서는 논의 중이거나 미결·검증 필요인 내용도 해당 상태를 표시하여 유지할 수 있으며, 확정된 내용과 구분한다. `[삭제 확정]`은 제안의 폐기, 작업 항목의 제외·분리·통합에 따른 대체, 기존 작업물의 실제 삭제에 관한 결정 중 무엇을 뜻하는지 대상과 이유·승인 범위를 구별하여 기록한다. 폐기·제외·대체된 작업 항목은 본문 제목과 변경 대장의 결정 상태에 같은 `[삭제 확정]`을 표시하고 기존 내용과 관련 결정 기록을 보존한다. 별도의 `[삭제]` 분류는 사용하지 않는다. 상태 표기 자체를 실제 작업의 실행 승인으로 보지 않는다.

상위 작업 항목 자체에 별도의 논의가 있는 경우에는 그 논의가 확정되고 모든 하위 작업 항목의 결정 상태가 각각 [확정] 또는 [삭제 확정]일 때, 별도의 사용자 승인이나 상태 변경에 대한 개별 동의 없이 상위 작업 항목을 [확정]으로 표시한다. 상위 작업 항목 자체에 별도의 논의가 없는 경우에는 모든 하위 작업 항목의 결정 상태가 각각 [확정] 또는 [삭제 확정]일 때 같은 방식으로 표시한다. 이 표시는 이미 결정된 논의의 상태를 종합한 것으로서 새로운 내용·범위 또는 실행을 승인하거나 실제 작업의 완료를 뜻하지 않는다.

사용자가 AI와 작업 항목에 관한 논의를 직접 시작하면 해당 작업 항목을 별도의 상태 변경 승인이나 개별 동의 없이 [논의 중]으로 표시한다. 하위 작업 항목 중 하나라도 [논의 중]으로 변경되면 상위 작업 항목도 함께 [논의 중]으로 표시한다. 이미 [확정]인 항목에서 논의가 다시 시작되는 경우에도 같은 방식으로 표시하되, 기존 확정 내용과 승인 기록은 보존하고 재논의 대상을 구분하여 기록한다. 이 상태 변경 자체를 기존 승인 내용의 변경이나 새로운 실행 승인으로 보지 않는다.

[검증 필요]는 검증이 필요한 해당 작업 항목에만 표시하고 상위 작업 항목으로 자동 전파하지 않는다. 하위 작업 항목이 [확정][검증 필요]인 경우 결정 상태는 [확정]이므로 상위의 자동 확정 조건을 판단할 때 확정된 하위 항목으로 본다. 상위의 확정 표시는 하위의 검증 완료를 뜻하지 않는다.

선행 결정 대기인 작업 항목도 사용자가 실제 논의를 시작하면 [논의 중]으로 표시하고, 미해결 선행 쟁점 ID·의존 이유·제약은 별도 기록으로 유지한다. 논의 중 전환으로 선행 조건이 해결된 것으로 보지 않는다. 아직 논의를 시작하지 않은 의존 항목은 [선행 결정 대기]를 유지한다. 하위 항목이 없는 작업은 자체 논의의 상태 기준을 따른다. 여러 단계의 상위 항목에는 같은 기준을 각 단계에 적용한다.

하위가 모두 [삭제 확정]이어도 상위 자체의 삭제 결정으로 취급하지 않는다. 위 상태 표시의 절차는 PROC-001 제4조(참조 기준 v1.10)를 따른다.

⑤ **변경 대장의 구성:** 제2항제4호의 변경 대장은 다음 각 호에 따라 구성한다.

1. **기본 표 구성:** Notion의 표 기능으로 작성하며, 기본 열은 `변경 ID | 작업 항목·대상 | 작업·변경 내용 | 결정 상태 | 작업 진행 상태 | 승인 기록·참조 | 완료 내용·결과 근거 | 남은 작업`으로 한다. 각 행은 개별 작업·변경 단위에 대응하며, 작업 항목 번호나 링크로 본문과 연결한다. 결정 상태는 제4항의 표기를 사용하고, 작업 진행 상태는 `미착수 / 진행 중 / 완료 / 보류`로 별도 표시한다. 일부만 완료한 항목은 ‘진행 중’으로 두고 완료 내용과 남은 작업을 나누어 기재한다. 완료 내용·결과 근거에는 실제 반영 위치나 검증 결과 등 확인 가능한 기록을 연결한다. 필요하면 일자, 이유·근거, 연쇄 영향, 검증 조건 및 `완료 수량 / 전체 수량` 열을 추가하며, 기존 기록은 ID·위치·링크로 참조한다. 승인이나 결정의 확정만으로 작업을 ‘완료’로 표시하지 않는다.
2. **변경 ID의 정의:** 변경 ID는 변경 대장에 등록한 개별 작업·변경 단위를 지속적으로 식별하고, 본문·승인 기록·결과 근거·변경 이력을 서로 연결하기 위한 고유 식별자이다. 작업 항목 번호는 본문의 계층과 위치를 나타내며, 변경 ID는 본문에서의 위치나 순서가 바뀌어도 동일한 작업·변경을 추적하는 데 사용한다.
3. **변경 ID의 부여:** 협업 작업 페이지별로 최초 등록 시 `CHG-001`부터 시작하여 등록 순서에 따라 `CHG-002`, `CHG-003`처럼 순차 부여한다. 숫자는 최소 세 자리로 표기하며 999를 넘으면 자릿수를 늘린다. 기존 대장에 ID가 있으면 이를 유지하고 새 항목에는 기존 최대 번호의 다음 번호를 부여한다. ‘기존 최대 번호’는 삭제·폐기를 포함하여 해당 페이지에서 역대 부여한 번호 중 가장 큰 번호를 뜻한다. 동일 페이지 안에서는 ID를 중복 부여하지 않으며, 삭제·폐기한 ID도 재사용하지 않는다. 폐기·제외·대체가 확정된 항목은 대장 행을 실제로 지우지 않고 결정 상태를 `[삭제 확정]`으로 표시하며, 기존 ID·내용과 처리 이유·관련 결정 기록을 보존한다. 연결된 본문 작업 항목에도 같은 상태를 표시한다. 동일 작업·변경의 내용·상태·순서가 바뀌어도 ID는 유지한다. 하나의 항목을 둘 이상으로 분리하거나 여러 항목을 하나로 통합하기로 확정한 경우, 기존 항목은 본문과 대장에서 `[삭제 확정]`으로 보존하고 현재 실행 작업·실제 작업 현황의 집계에서 제외한다. 논의·결정 현황에서는 삭제 확정도 전체와 완료에 포함한다. 새 항목에는 각각 새 변경 ID를 부여하고 기존 항목과 새 항목 사이의 대체 관계를 양쪽 기록에 연결한다. 다른 협업 작업 페이지의 항목을 참조할 때에는 해당 페이지 링크와 변경 ID를 함께 표기한다.
4. **진행 현황 요약:** 논의·결정 현황과 실제 작업 현황을 구분하여 요약한다. 논의·결정 현황의 미착수는 결정 상태가 [제기] 또는 [선행 결정 대기]인 항목의 건수, 진행 중은 [논의 중]인 항목의 건수, 완료는 [확정] 또는 [삭제 확정]인 항목의 건수로 한다. 논의·결정 현황에는 보류를 두지 않는다. 집계 대상은 대장의 중복 없는 최하위 작업·변경 단위로 하며 삭제 확정을 전체와 완료에 모두 포함한다. 논의 완료율은 (확정 건수+삭제 확정 건수)/전체 건수×100%로 계산하고, 전체가 0이면 ‘해당 없음’으로 표시한다. 검증 필요는 해당 항목의 별도 플래그로 관리하고 세 단계 분류를 바꾸지 않는다. 이 집계는 결정 상태의 요약이며, 항목별 본문과 대장의 원래 결정 상태를 세 단계 명칭으로 바꾸지 않는다. 논의·결정의 완료와 실제 작업의 완료는 구분한다. 논의·결정 현황과 실제 작업 현황은 별도 표로 둔다. 실제 작업 현황은 작업 진행 상태의 미착수·진행 중·완료·보류를 기준으로 별도 표에 요약한다. 집계 대상은 대장에 등록된 중복 없는 최하위 작업·변경 단위로 하며, 결정 상태가 `[삭제 확정]`이고 그 사유가 제안 폐기 또는 작업 항목의 제외·대체인 항목은 실제 작업 집계에서 제외하여 별도 표시한다. 실제 작업물의 삭제를 수행하는 작업은 `[삭제 확정]`이라는 상태만으로 집계에서 제외하지 않고, 해당 삭제 작업의 진행 상태에 따라 집계한다. 전체는 집계 대상의 총건수이며, 미착수·진행 중·완료·보류는 각각 해당 작업 진행 상태의 건수로 한다. 보류 건수를 별도 기재하여 빠진 건수가 추적되게 한다. 검증 필요는 해당 항목의 별도 중복 플래그로 표시한다. 완료율은 완료 건수를 전체 건수로 나누어 산출하며, 전체가 0건이면 ‘해당 없음’으로 표시한다. 두 현황의 완료율은 작업 건수 기준이며 작업량·소요 시간의 비율과 구분한다.

⑥ **변경 이력 표의 형식:** 제2항제5호는 Notion의 표 기능으로 작성하며 기본 열은 `일자 | 변경 대상 | 변경 내용 | 변경 이유 | 사용자 결정·승인 참조`으로 한다. 변경 이유에는 필요 시 폐기·제외의 범위와 재도입을 경계해야 하는 조건을 명시한다. 변경 이력은 현행 지시를 이해하기 위한 참고 정보이며, 과거 지시를 실행하거나 복원하는 근거로 사용하지 않는다. 단순 오탈자 등 실행 판단에 영향이 없는 수정은 간략히 기록할 수 있다. 버전 열은 두지 않는다.

⑦ **정합성과 우선순위:** 제3절의 현행 실행 명령, 제4절의 변경 대장 및 제5절의 변경 이력이 상충하면 해당 항목을 임의로 해석하거나 수행하지 않고 상충 사항을 보고한다. 변경 대장이나 변경 이력으로 현행 본문의 승인 범위를 확대·축소하지 않는다. 협업 작업 페이지의 변경 및 기록 관리 기준은 제6조에 따른다.

## 제5조(절·항목 및 표기)

① **제목 계층:** 협업 작업 페이지의 제목은 Notion의 페이지 제목으로 작성하며, 본문 주요 절은 ‘제목 1’, 제4조의 작업 항목 `3.1` 등은 ‘제목 2’, 그 하위 작업 항목 `3.1.1` 등은 ‘제목 3’ 기능으로 표시한다. 제목 계층은 페이지 구조를 나타내는 서식이며, 작업 항목 번호는 해당 작업을 식별하는 번호로서 서로 구분한다.

② **목록·표·예시 및 부록:** 사용자가 정보를 읽고 이해하는 방식에 맞춰 다음 각 호에 따라 Notion의 표시 기능을 사용한다.

1. **번호 목록:** 작업의 순서나 선후 관계가 있을 때 사용한다.
2. **글머리표 목록:** 순서 없이 여러 조건이나 사항을 나열할 때 사용한다.
3. **표:** 같은 항목을 기준으로 내용을 비교하거나 상태·진행 현황을 확인할 때 사용한다.
4. **예시:** 규칙만으로 실제 작성 모습을 이해하기 어려울 때 사용한다.
5. **부록:** 반복해서 참고할 양식·예시나 본문에 두면 흐름을 끊는 긴 보충 자료를 둔다.
6. **본문과 상세 설명:** 본문에는 현재 판단에 필요한 내용을 남기고, 상세 설명은 필요한 경우 Notion의 토글 기능으로 접어둘 수 있다.
7. **예시·부록의 작성 원칙:** 예시와 부록은 필요한 경우에만 사용하며, 본문의 규칙을 설명·보완하는 범위에서 작성한다. 예시나 부록에서 새로운 의무를 추가하지 않는다.

제4조제3항의 `(1)`, `(2)` 등 세부 구분은 제목 기능으로 표시하지 않고 일반 텍스트나 목록으로 작성한다.

③ **식별자 표기:** 변경 ID·파일 위치·함수명·식 번호 등 추적에 필요한 식별자는 원문과 일치하도록 기재하며, 제2조제2항의 원문 유지 원칙을 따른다.

④ **표기 일관성:** 동일한 종류의 정보에는 페이지 전체에서 일관된 Notion 표시 형식을 사용한다. 표·목록·제목 계층을 조정하더라도 작업 항목의 식별 번호와 참조 관계가 불명확해지지 않도록 한다.

⑤ **근거 작성:** 협업 작업 페이지에서 근거를 작성·제시할 때에는 [TPL-003 — 근거 제시 규정](https://app.notion.com/p/TPL-003-3f44e2f6c2f181cda573f567cfa51683?pvs=21)(참조 기준 v1.0)을 따른다. 출처·확인 위치, 근거 종류·신뢰도 및 미확인 자료의 표기·취급 등 구체적인 작성 방식은 해당 규칙을 적용한다.

## 제6조(협업 작업 페이지의 변경 및 기록 관리)

① **관리 대상의 구분:** 협업 작업 페이지에서 논의한 쟁점·결정·변경과 작업 진행 현황은 작업 기록과 변경 대장으로 추적하며, 기록 관리 절차는 PROC-001 제6조를 따른다. 제4조제2항제5호의 ‘협업 작업 페이지 변경 이력’에는 사용자가 페이지의 주요 변경과 그 이유를 확인할 수 있도록 요약한다. 변경 대장은 개별 작업·변경의 상태와 진행을, 변경 이력은 페이지 자체의 변화를 보여 주는 기록으로 구분하며, 같은 내용을 전부 중복해서 수록하지 않는다.

② **변경 기록 및 승인 추적:** 변경 관리에서는 다음 각 호를 따른다.

1. 변경 대장의 구성은 제4조제5항에 따르며, 작업 기록과 승인 기록은 기존 ID·위치·링크로 연결한다.
2. 변경 대상이 다른 작업 항목·정의·참조·검증 기준에 영향을 미치면 PROC-001 제7조에 따라 연쇄 영향을 점검한다. 기존 기록의 ID·위치·링크를 활용하여 불필요한 중복 작성을 피한다.
3. 승인되지 않은 변경안과 승인된 실행 항목을 구분하고, 사용자의 승인 및 PROC-001 제4조의 상태 변경 요건을 충족하지 않은 내용을 임의로 확정하지 않는다.

③ **버전·지위의 구분:** 협업 작업 페이지에는 문서 버전을 부여하거나 갱신하지 않으며, 가안·정식 지위를 구분하지 않는다. 개별 작업 항목의 결정 상태·승인 기록과 변경 대장은 계속 관리한다. 규칙 자체의 개정 버전 제도는 이 기준의 폐지 대상이 아니다. 페이지의 작성·전달은 PROC-001의 논의 종결·컴파일·이관 요건이나 개별 작업의 실행 승인을 대신하지 않는다.

④ **작성 기준일과 변경 기록:** 최초 작성일은 페이지명과 머리말의 작성 기준일로 고정하고 최신 수정일과 구분한다. 같은 날이나 다른 날 편집해도 최초 작성일은 바꾸지 않으며 실제 수정일은 제5항의 변경 이력에 기록한다. 기존 버전 표지·승인·변경·폐기 이유 등 과거 기록은 역사 기록으로 보존한다. 후속 페이지가 기존 작업을 잇는 경우 기존 페이지·CHG-ID·승인 기록을 연결한다.

⑤ **변경 이력의 작성:** 제4조제2항제5호와 제4조제6항에 따라 Notion의 표 기능으로 작성하며, 기본 열은 `일자 | 변경 대상 | 변경 내용 | 변경 이유 | 사용자 결정·승인 참조`으로 한다. ‘변경 대상’은 가능한 한 작업 항목 번호 또는 식별자로 연결하고, ‘사용자 결정·승인 참조’에는 사용자 승인 기록 또는 확인 가능한 참조를 기재한다. 폐기·삭제의 이유 및 현재 제외 범위는 사용자가 변경 경위와 현재 적용 내용을 이해하는 데 필요할 때 명시한다. 버전 열은 두지 않는다.

⑥ **실행 명령과의 분리:** 변경 이력은 현행 지시를 이해하기 위한 참고 정보이며, 과거안을 복원하거나 실행할 권한을 부여하지 않는다. 현행 지시와 변경 이력 사이에 해소되지 않은 상충이 발견되면 PROC-001과 GOV-001의 중단·보고 원칙에 따라 처리한다.

## 제7조(문장 작성 방식)

협업 작업 페이지에서 AI는 사용자가 내용을 쉽게 이해하고 판단할 수 있도록 다음 각 호에 따라 서술한다.

1. 명령형을 일률적으로 쓰지 않고, 내용에 맞는 자연스러운 설명형 문장으로 쓴다.
2. 핵심을 먼저 쓰고, 이유와 세부 설명은 뒤에 둔다.
3. 한 문장에는 하나의 판단이나 요구만 담는다.
4. 무엇을, 왜 하는지, 어떤 결과를 기대하는지 구체적으로 쓴다.
5. '적절히', '필요에 따라'처럼 해석이 갈리는 표현을 쓸 때는 그 기준을 함께 쓴다.
6. 확인된 사실과 AI의 해석·추측·제안이 문장에서 구분되도록 쓰고, 확인되지 않은 내용은 단정적으로 쓰지 않는다.
7. 사용자가 결정할 내용이 있으면 결정할 내용, 선택지, AI의 권고와 그 이유를 쓴다.

## 제8조(전달 대상·내용 및 매체)

① **전달 대상:** 협업 작업 페이지의 전달 대상은 사용자로 한다.

② **전달 내용:** 사용자가 작업 내용, 결정 상태, 논의 경과, 변경 대장, 변경 이력 및 남은 작업을 확인할 수 있도록 하나의 협업 작업 페이지에 정리한다. 관련 원본·참조 자료와 상세 기록은 필요한 위치에 연결한다.

③ **전달 매체:** 전달 매체는 Notion 페이지로 한다. 사용자가 해당 페이지와 연결된 자료에 접근하여 내용을 확인할 수 있도록 구성한다.

④ **전달과 실행 승인의 구분:** 협업 작업 페이지의 작성·승인·전달은 실제 파일 수정이나 작업 실행의 자동 승인을 뜻하지 않는다.

## 제9조(양식 점검 및 예외)

① 협업 작업 페이지를 전달하기 전에 페이지 형식, 머리말, 필수 절, 식별자, 산출물 명세, 연결 자료의 접근 가능성 및 사용자가 내용을 이해할 수 있는지를 확인한다. 페이지 전달 전 작업 목적·범위와 최종 결과물의 명세가 대응하고 누락이 없는지 확인한다.

② 형식상의 편의를 이유로 GOV-001 및 PROC-001의 승인·검증·중단 요건을 완화하지 않는다.

③ 특수한 형식이 필요한 경우 예외의 필요성·적용 범위·호환성·승인 여부를 명시하고 별도로 논의한다.

④ **원문 및 관련 기록의 확인:** 협업 작업 페이지의 전달 및 PROC-001에 따른 컴파일 전에 명시한 수정 위치·참조 범위를 확인한 원문과 대조한다. 이후 원본·관련 자료의 변경이나 새로운 참조를 알게 되면 영향을 받는 범위를 재확인하고 작업 항목·변경 대장의 관련 기록을 갱신한다. 확인하지 못한 자료·위치는 확인된 적용 대상으로 단정하지 않고 이유·영향·필요한 확인 사항을 남긴다. 확인 범위는 해당 작업의 판단·수정에 필요한 자료·위치·사례로 한정한다. 미확인 자료의 근거 표기·취급과 연쇄 영향 처리·상충 시 조치는 각각 TPL-003·PROC-001·GOV-001을 따른다.

⑤ **저장 후 서식 검증:** 협업 작업 페이지의 작성 또는 서식 변경 후 전달 전에 저장된 결과를 다시 확인하여 제목 계층·표의 형식과 열 구성·너비·상태 글자색 등 적용한 서식이 이 규칙에 맞게 반영되었는지 점검한다. 새 페이지에서는 적용한 서식을, 서식 변경 시에는 변경 부분과 직접 영향을 받는 서식을 점검한다. 서식 값의 저장 여부와 화면 표시의 확인 여부를 구분하여 확인 결과·불일치·미확인 범위를 간단히 기록한다. 이 항의 검증 범위는 서식으로 한정한다.

    # 4. 변경 대장
    
    **논의·결정 현황**
    
    | 전체 | 미착수 | 진행 중 | 완료 | 검증 필요 | 논의 완료율 |
    | --- | --- | --- | --- | --- | --- |
    | N건 | U건 | P건 | C건 | V건 | C/N × 100% |
    - 논의·결정 현황과 실제 작업 현황을 구분하여 요약한다. 논의·결정 현황의 미착수는 결정 상태가 [제기] 또는 [선행 결정 대기]인 항목의 건수, 진행 중은 [논의 중]인 항목의 건수, 완료는 [확정] 또는 [삭제 확정]인 항목의 건수로 한다. 논의·결정 현황에는 보류를 두지 않는다. 집계 대상은 대장의 중복 없는 최하위 작업·변경 단위로 하며 삭제 확정을 전체와 완료에 모두 포함한다. 논의 완료율은 (확정 건수+삭제 확정 건수)/전체 건수×100%로 계산하고, 전체가 0이면 ‘해당 없음’으로 표시한다. 검증 필요는 해당 항목의 별도 플래그로 관리하고 세 단계 분류를 바꾸지 않는다. 이 집계는 결정 상태의 요약이며, 항목별 본문과 대장의 원래 결정 상태를 세 단계 명칭으로 바꾸지 않는다. 논의·결정의 완료와 실제 작업의 완료는 구분한다.
    
    **실제 작업 현황**
    
    | 전체 | 미착수 | 진행 중 | 완료 | 보류 | 검증 필요 | 작업 완료율 |
    | --- | --- | --- | --- | --- | --- | --- |
    | N건 | U건 | P건 | C건 | H건 | V건 | C/N × 100% |
    - 실제 작업 현황은 작업 진행 상태의 미착수·진행 중·완료·보류를 기준으로 별도 표에 요약한다. 집계 대상은 대장에 등록된 중복 없는 최하위 작업·변경 단위로 하며, 결정 상태가 `[삭제 확정]`이고 그 사유가 제안 폐기 또는 작업 항목의 제외·대체인 항목은 실제 작업 집계에서 제외하여 별도 표시한다. 실제 작업물의 삭제를 수행하는 작업은 `[삭제 확정]`이라는 상태만으로 집계에서 제외하지 않고, 해당 삭제 작업의 진행 상태에 따라 집계한다. 전체는 집계 대상의 총건수이며, 미착수·진행 중·완료·보류는 각각 해당 작업 진행 상태의 건수로 한다. 보류 건수를 별도 기재하여 빠진 건수가 추적되게 한다. 검증 필요는 해당 항목의 별도 중복 플래그로 표시한다. 완료율은 완료 건수를 전체 건수로 나누어 산출하며, 전체가 0건이면 ‘해당 없음’으로 표시한다. 두 현황의 완료율은 작업 건수 기준이며 작업량·소요 시간의 비율과 구분한다.

    - 표의 한 행은 개별 작업·변경 단위에 대응한다. 변경 ID는 제4조제5항제2·3호에 따라 부여·유지하며, 삭제·폐기를 포함한 역대 최대 번호의 다음 번호를 사용한다.
    - 폐기·제외·대체된 항목은 행을 지우지 않고 결정 상태에 `[삭제 확정]`을 표시한다. 연결된 본문 제목에도 같은 상태를 표시하며, 기존 ID·내용과 처리 이유·관련 결정 기록을 보존한다. 분리·통합 시 기존 항목은 현재 실행 작업·실제 작업 현황의 집계에서 제외하되 논의·결정 현황에는 삭제 확정으로 포함한다. 새 항목에 새 ID를 부여하며 양쪽 기록에 대체 관계를 연결한다.

**작성 시 유의**

- 상위 자체 논의가 있으면 그 논의도 확정되고 모든 하위가 [확정] 또는 [삭제 확정]일 때, 자체 논의가 없으면 모든 하위가 두 상태 중 하나일 때 상위를 별도 승인·개별 동의 없이 [확정]으로 표시한다. 모두 삭제 확정이어도 상위 자체의 삭제 결정은 아니다. 사용자가 AI와 실제 직접 논의를 시작하면 [논의 중]으로 표시하고, 하위 하나라도 논의 중이면 각 상위에도 전파한다. 단순 언급과 실제 논의 시작을 구분한다. 확정 후 재논의는 기존 확정·승인 기록과 재논의 범위를 나누어 보존한다. 선행 결정 대기도 실제 논의 시작 시 같은 예외를 적용하지만 미해결 선행 쟁점 ID·의존 이유·제약을 별도 기록하며 미시작 의존 항목은 대기를 유지한다. 하위 없는 항목은 자체 논의 상태를 따른다. 검증 필요는 해당 항목에만 표시하며 상위로 전파하지 않는다. 확정+검증 필요는 상위 종합 확정을 막지 않으나 하위 검증 완료를 뜻하지 않는다. 이는 상태 표시의 예외로 내용·범위·삭제·실행 승인이나 실제 작업 완료를 대신하지 않는다. TPL 제4조제4항·PROC 제4조(참조 기준 v1.10)를 함께 따른다.
- 근거의 구체적인 작성·표기 방식은 [TPL-003 — 근거 제시 규정](https://app.notion.com/p/TPL-003-3f44e2f6c2f181cda573f567cfa51683?pvs=21)(참조 기준 v1.0)을 따른다.
- 논의 경과와 미승인·미결·검증 필요 사항도 상태를 구분하여 기록할 수 있다. 필요하면 Notion 토글·페이지 멘션·링크로 상세 기록을 연결한다.
- 협업 작업 페이지에 버전·가안/정식 지위를 두지 않으며 최초 작성일과 변경 기록은 제6조를 따른다. 실제 수정일·사용자 결정·승인 참조와 과거 기록을 보존한다.
- 전달 대상은 사용자이고 전달 매체는 Notion 페이지이다. 페이지의 작성·승인·전달만으로 실제 작업의 실행이 승인된 것으로 보지 않는다.
- 실행 지시 문서의 구성·출력 양식은 TPL-002에서 다루며, 이 협업 페이지 양식과 구분한다.

## 부록 B. 설계 쟁점 및 처리 결과

- **TPL-001-Q01 [확정]:** 산출물 파일명은 대상·용도·필요한 버전 등을 식별할 수 있으면 되며, 고정된 파일명 규칙을 일률적으로 요구하지 않는 것으로 정하였다. 제2조제5항에 반영하였다. 협업 작업 페이지의 이름은 산출물 파일명과 구분하여 제2조제4항을 따른다.
- **TPL-001-Q02 [확정]:** TPL-001의 적용 대상을 최종 실행 지시서에서 Notion 협업 작업 페이지로 변경함에 따라, 기존 ‘표준 절 9개’의 제목·순서 및 통합 여부에 관한 쟁점은 종료한다. 협업 작업 페이지의 본문은 제4조제2항의 6개 절 구성을 기준으로 하며, 제6절 ‘실행 제외 항목’은 선택 항목으로 둔다. 최종 실행 지시서의 구성은 TPL-002에서 다룬다.
- **TPL-001-Q03 [확정]:** 제3조제2항의 문서 버전·문서 상태·작업 목적·작업 범위는 필수 항목으로, 제3조제3항의 작성 기준일·문서 식별자는 선택 항목으로 정하고 해당 조항에 명시하였다.
- **TPL-001-Q04 [확정]:** TPL-001의 적용 대상을 Notion 협업 작업 페이지로 변경하고, 제2조제3항 및 제8조제3항에 따라 작성·전달 매체를 Notion 페이지로 정하였다. 원본·참조 자료와 상세 기록은 제8조제2·3항에 따라 페이지에서 연결하고 사용자가 접근할 수 있도록 한다. 최종 Markdown(`.md`) 실행 지시서의 출력·전달 형식은 TPL-002에서 다룬다.
- **TPL-001-Q05 [확정]:** 제5조제2항에 사용자가 정보를 읽고 이해하는 방식을 기준으로 번호 목록·글머리표·표·예시·부록의 사용 기준을 명시하였다. 순서·선후 관계는 번호 목록, 순서 없는 나열은 글머리표, 비교·상태·진행 현황은 표, 작성 모습의 이해를 돕는 내용은 예시, 반복 참조 양식이나 긴 보충 자료는 부록으로 구분하였다. 본문에는 현재 판단에 필요한 내용을 남기고 상세 설명에는 Notion 토글을 사용할 수 있도록 하며, 예시·부록에서 새로운 의무를 추가하지 않는 원칙을 반영하였다.
- **TPL-001-Q06 [확정]:** 제4조제1항·제2항제3호·제4항 후단 및 제6조제1항을 사용자와 공유하는 협업 작업 페이지의 문구로 수정하고, 제4조제3항의 마지막 하위 절 명칭을 ‘공통 작업·확인·기록 조건’으로 맞추었다. 부록 A도 현행 TPL-001에 맞춘 Notion 협업 작업 페이지 표준 양식으로 교체하여 논의·미결 기록, 변경 대장 및 진행 현황을 포함하였다. 최종 실행 지시서의 양식은 TPL-002의 영역으로 구분하였다.

## 제1조(목적·적용 범위·협업 작성 환경 및 타 규칙과의 관계)

① **목적:** 이 문서(TPL-001)는 사용자와 설계 AI가 Notion에서 작업 내용을 공동으로 작성·논의·검토·수정하는 협업 작업 페이지의 구성과 표기 형식을 정하는 것을 목적으로 한다. 협업 작업 페이지는 작업 항목과 결정 상태, 논의 경과 및 변경 내용을 식별·추적하고, 가안 문서와 정식 문서의 버전을 구분하여 관리하는 공간으로 사용한다.

② **적용 범위:** 이 문서는 PROC-001에 따른 협업 작업 페이지의 작업 항목 구성, 상태 표기와 색상, 작업 기록, 변경 대장 및 가안·정식 문서의 버전 관리 형식에 적용한다. 작업 대상은 프로젝트 전체뿐 아니라 논문의 특정 장, 게임의 개별 오브젝트, 코드의 특정 기능 등 사용자가 지정한 개별 작업 단위를 포함한다. 이 문서는 협업 작업 페이지의 양식이며, 실행 AI에게 전달하는 최종 실행 지시서 자체의 출력 양식으로 적용하지 않는다.

③ **협업 작성 환경:** 사용자와 설계 AI는 하나의 Notion 협업 작업 페이지를 공동 작성·논의의 기준 공간으로 사용한다. 작업 내용, 결정 상태, 작업 기록, 변경 대장 및 문서 버전 사이의 관계를 사용자가 확인하고 추적할 수 있도록 구성하며, 상태 색상·토글·콜아웃·페이지 멘션 등 Notion의 편집·표시 기능을 활용할 수 있다. 협업 작업 페이지에는 미결·논의 중·검증 필요 사항과 확정된 내용을 구분하여 기록할 수 있으며, 페이지의 기재 내용이나 정식 문서로의 승격만으로 실제 작업의 실행이 승인된 것으로 보지 않는다.

④ **타 규칙과의 관계:** GOV-001은 공통 원칙을, PROC-001은 논의·승인·상태 변경·검증·컴파일·이관 및 실행에 관한 절차를 정하며, 이 문서(TPL-001)는 그 절차에 사용하는 Notion 협업 작업 페이지의 형식을 정한다. 실행 AI에게 전달하는 최종 Markdown(`.md`) 실행 지시서의 구성·형식·출력 규격은 별도 신설 예정인 TPL-002에서 정한다. 협업 작업 페이지의 내용을 최종 실행 지시서로 정리·전달할 때에는 PROC-001의 해당 요건을 따르며, 협업 기록과 실행 지시를 구분한다. 이 문서의 형식 규칙은 GOV-001 및 PROC-001의 승인·검증·중단 요건을 변경하거나 대신하지 않는다.

## 제2조(작성 언어·페이지 형식 및 식별)

① **작성 언어:** 협업 작업 페이지는 한국어로 작성한다. 널리 통용되는 한국어 기술 용어는 한국어 표기만 사용할 수 있으며, 그렇지 않은 기술 용어는 처음 등장하는 위치에서 한국어 표현과 원어를 병기하고 이후에는 의미가 명확한 경우 한국어 표현만 사용할 수 있다. 통용 여부의 판단이 어려우면 병기한다.

② **원문 유지:** 다음 각 호는 번역하거나 바꾸어 쓰지 않고 원문 그대로 표기한다.

1. 파일명·폴더명·경로
2. 원본 자료의 시트명·열 이름·제목·식별자(ID) 등 실행 AI가 원본과 대조해야 하는 명칭
3. 코드·명령어·함수명·변수명·수식
4. 원문 인용

③ **페이지 형식:** 협업 작업 공간은 Notion 페이지로 작성한다. 페이지의 구성과 표기는 사용자가 작업 내용·결정 상태·논의 경과 및 변경 내용을 쉽게 읽고 확인할 수 있도록 한다.

④ **페이지명:** 협업 작업 페이지의 이름은 `작업공간_`으로 시작하고, 그 뒤에 작업 목표와 문서 버전을 밑줄(`_`)로 구분하여 붙인다. 페이지명에는 공백과 대괄호 등 특수문자를 사용하지 않는다. 예: `작업공간_논문2장작성_v1.0`. 버전 부여 및 확정 기준은 제6조에 따른다.

⑤ **산출물과의 구분:** 협업 작업 페이지의 형식은 해당 작업에서 생성되는 실제 작업 산출물의 파일 형식과 구분한다. 작업 산출물별 종류·수량·형식 등은 협업 작업 페이지에서 논의·정리하며, 최종 실행 지시서에는 PROC-001 제8조제1항제2호에 따라 명시한다. 산출물의 파일명은 대상과 용도, 필요한 경우 버전을 식별할 수 있도록 정하며, 이 양식에서 고정된 파일명 규칙을 일률적으로 요구하지 않는다.

⑥ **Notion 표시 형식:** 협업 작업 페이지는 사용자가 내용을 쉽게 알아보고 확인할 수 있도록 다음 각 호에 따라 작성한다.

1. 표는 Notion의 표 기능을 사용하여 읽기 쉬운 형태로 작성한다.
2. 상태 색상·토글·콜아웃·페이지 멘션 등 Notion의 편집·표시 기능을 활용할 수 있으며, 같은 종류의 정보에는 일관된 형식을 적용한다.
3. 도구별 실행 방식이 필요한 경우에는 본문과 분리된 부록에 둔다.

## 제3조(페이지 머리말)

① **페이지 제목:** 협업 작업 페이지의 제목은 작업 대상을 구체적으로 식별할 수 있도록 작성하며, 페이지명은 제2조제4항에 따른다.

② **머리말 표:** 페이지 제목 다음에는 2열 표를 배치한다. 첫 번째 열에는 항목명을, 두 번째 열에는 해당 값을 기재하며, 다음 각 호의 항목은 필수로 포함하고 아래 순서대로 배치한다.

1. **문서 버전:** 해당 협업 작업 페이지의 문서 버전. 구체적인 부여 기준은 제6조에 따른다.
2. **문서 상태:** 협업 작업 페이지 자체의 작성·승인 상태. 개별 쟁점의 결정 상태와 구분한다.
3. **작업 목적:** 이번 작업을 통해 달성하려는 핵심 목표를 간결하게 기술한다.
4. **작업 범위:** 이번 작업의 적용 대상 및 제외되는 범위를 요약한다.

③ **선택 항목:** 작성 기준일과 문서 식별자는 선택 항목으로 하며, 필요한 경우 표에 추가할 수 있다. 작성 기준일을 추가할 때에는 문서 상태 다음, 작업 목적 앞에 배치한다. 문서 식별자의 배치 위치는 별도 합의가 없으면 문서 버전 앞에 둔다.

④ **작성 원칙:** 머리말에는 작업 식별과 개요 파악에 필요한 정보만 기재한다. 산출물 상세 명세·변경 내용·검증 기준 등은 본문에 두며, 머리말과 본문의 목적·범위·상태가 서로 일치해야 한다.

⑤ **Notion 표 형식:** 머리말 표는 Notion의 표 기능을 이용하여 2열 표로 작성한다. 표는 페이지의 사용 가능한 너비를 충분히 활용하며, ‘항목’ 열은 항목명을 읽을 수 있는 최소한의 너비로 두고 ‘내용’ 열에는 나머지 너비를 최대한 배정한다. 내용이 가능한 한 한 줄로 표시되도록 ‘내용’ 열의 너비를 넉넉하게 확보한다. 셀 안에서 줄바꿈을 강제하지 않으며, 표시 공간을 넘는 내용은 의미를 유지하면서 간결한 문장으로 정리한다.

⑥ **표준 작성 예시:** 페이지 머리말의 표준 작성 예시는 부록 D에 둔다.

## 제4조(본문의 기본 절 구성)

① **구성 원칙:** 협업 작업 페이지의 본문은 사용자가 작업 내용과 목적, 결정 상태, 논의 경과 및 진행 현황을 이해하고 판단할 수 있는 정보로 구성한다. 확정된 내용뿐 아니라 논의 경과·대안 비교·미승인 제안·미결 사항도 서로 구분하여 기록할 수 있다. 상세 내용은 필요한 위치에 연결하고, 현재 판단에 필요한 근거·제약·확인 기준은 본문에서 쉽게 확인할 수 있도록 한다.

② **표준 절:** 본문은 다음 각 호의 절로 구성한다.

1. **작업 목적·대상 및 입력 자료:** 작업의 목적, 원본의 파일명·버전·위치 또는 식별 방법, 참조 자료, 작업 대상과 적용 위치, 착수 전 확인 사항 및 불일치 시 중단 조건을 기술한다.
2. **산출물 명세:** 산출물별 종류·개수·내용 범위·파일 형식·파일명 또는 명명 규칙·저장 및 제공 위치·필수 구성·수용 기준을 명시한다. 원본 보존·덮어쓰기 여부 및 개수가 달라지는 조건도 기술한다.
3. **작업 수행 명세:** 사용자와 함께 검토할 작업을 계층형 항목으로 구분하고, 각 항목에 작업 대상, 하려는 일, 기대하는 결과, 필요한 근거, 보존·금지 조건 및 완료·확인 기준을 정리한다. 논의할 내용과 확정된 내용은 결정 상태로 구분하며, 불확실성이나 문제가 있으면 이유·영향 범위·필요한 확인 사항을 함께 기록한다. 작업 전체에 공통인 조건과 확인·진행 기록 방식은 제3절의 마지막 하위 절에 두고, 앞선 작업 항목에서 참조할 수 있다. 완료한 내용·확인 결과·실제 반영 위치·남은 작업은 제4절의 변경 대장과 연결하여 사용자가 진행 현황을 확인할 수 있도록 한다.
4. **변경 대장:** 작업·변경 항목별 결정 상태와 작업 진행 상태, 완료한 내용 및 남은 작업을 Notion 표로 정리한다. 표의 열 구성과 진행 현황 요약 형식은 제5항에 따른다.
5. **지시 문서 변경 이력:** 지시 문서 자체의 버전별 주요 변경 대상·변경 내용·이유를 표로 정리한다. 삭제·폐기한 지시가 다시 도입되는 것을 방지할 필요가 있으면 제외 이유와 현재 적용 범위를 식별할 수 있도록 한다.
6. **실행 제외 항목(선택):** PROC-001 제9조제2항에 따라 참고로 전달하는 미결·보류·검증 필요 사항을 둔다. 이 절의 내용은 실행 명령이 아니며, 실행 AI는 이를 수행하지 않는다.

③ **작업 수행 명세의 계층:** 제3절은 `3.1`부터 `3.n-1`까지를 개별 작업 항목으로 구성하고, 마지막 `3.n`을 **공통 작업·확인·기록 조건** 절로 둔다. `n`은 실제 하위 절 수에 따라 정하며 고정 번호 `3.2`를 강제하지 않는다. `3.1`, `3.1.1` 등 숫자 계층으로 식별하는 단위를 **작업 항목**이라 한다. 작업 항목은 필요에 따라 `3.1.1`까지 세분할 수 있다. 그보다 세밀한 내용을 나눌 필요가 있을 때 사용하는 `(1)`, `(2)`, `(3)` 등의 괄호 번호는 **세부 구분**이라 하며, 작업 항목으로 간주하지 않는다. 세부 구분은 필요한 경우에만 사용한다. 상위 항목은 작업 대상과 목표를, 하위 항목은 실제 수행 내용을 구체화한다. 각 항목에 필요한 근거는 원본과 대조 가능한 식별자 또는 출처로 연결하며, 불필요한 근거나 반복 설명은 생략한다.

④ **결정 상태의 처리 및 색상:** PROC-001에 따른 논의 중에는 `3.1`, `3.1.1` 등 모든 계층의 **작업 항목** 제목 끝에 결정 상태를 표시한다. `(1)`, `(2)` 등의 **세부 구분**에는 별도의 결정 상태를 붙이지 않으며, 해당 내용은 소속 작업 항목의 상태를 따른다. Notion에서 공동 작성하는 동안 상태 표기의 **글자색**은 다음 각 호와 같이 구분한다.

1. **[제기]:** 빨간색
2. **[논의 중]:** 노란색
3. **[확정]:** 초록색
4. **[삭제 확정]:** 보라색
5. **[선행 결정 대기]:** 파란색
6. **[검증 필요]:** 주황색. 결정 상태에 덧붙이는 검증 플래그로서 `[확정][검증 필요]`와 같이 표기하며, 별도의 결정 상태로 간주하지 않는다.

상태 색상은 Notion의 글자색 기능을 이용하여 해당 상태 텍스트에만 적용한다. 협업 작업 페이지에서는 논의 중이거나 미결·검증 필요인 내용도 해당 상태를 표시하여 유지할 수 있으며, 확정된 내용과 구분한다. `[삭제 확정]`은 제안의 폐기, 작업 항목의 제외·분리·통합에 따른 대체, 기존 작업물의 실제 삭제에 관한 결정 중 무엇을 뜻하는지 대상과 이유·승인 범위를 구별하여 기록한다. 폐기·제외·대체된 작업 항목은 본문 제목과 변경 대장의 결정 상태에 같은 `[삭제 확정]`을 표시하고 기존 내용과 관련 결정 기록을 보존한다. 별도의 `[삭제]` 분류는 사용하지 않는다. 상태 표기 자체를 실제 작업의 실행 승인으로 보지 않는다.

⑤ **변경 대장의 구성:** 제2항제4호의 변경 대장은 다음 각 호에 따라 구성한다.

1. **기본 표 구성:** Notion의 표 기능으로 작성하며, 기본 열은 `변경 ID | 작업 항목·대상 | 작업·변경 내용 | 결정 상태 | 작업 진행 상태 | 승인 기록·참조 | 완료 내용·결과 근거 | 남은 작업`으로 한다. 각 행은 개별 작업·변경 단위에 대응하며, 작업 항목 번호나 링크로 본문과 연결한다. 결정 상태는 제4항의 표기를 사용하고, 작업 진행 상태는 `미착수 / 진행 중 / 완료 / 보류`로 별도 표시한다. 일부만 완료한 항목은 ‘진행 중’으로 두고 완료 내용과 남은 작업을 나누어 기재한다. 완료 내용·결과 근거에는 실제 반영 위치나 검증 결과 등 확인 가능한 기록을 연결한다. 필요하면 일자, 이유·근거, 연쇄 영향, 검증 조건 및 `완료 수량 / 전체 수량` 열을 추가하며, 기존 기록은 ID·위치·링크로 참조한다. 승인이나 결정의 확정만으로 작업을 ‘완료’로 표시하지 않는다.
2. **변경 ID의 정의:** 변경 ID는 변경 대장에 등록한 개별 작업·변경 단위를 지속적으로 식별하고, 본문·승인 기록·결과 근거·변경 이력을 서로 연결하기 위한 고유 식별자이다. 작업 항목 번호는 본문의 계층과 위치를 나타내며, 변경 ID는 본문에서의 위치나 순서가 바뀌어도 동일한 작업·변경을 추적하는 데 사용한다.
3. **변경 ID의 부여:** 협업 작업 페이지별로 최초 등록 시 `CHG-001`부터 시작하여 등록 순서에 따라 `CHG-002`, `CHG-003`처럼 순차 부여한다. 숫자는 최소 세 자리로 표기하며 999를 넘으면 자릿수를 늘린다. 기존 대장에 ID가 있으면 이를 유지하고 새 항목에는 기존 최대 번호의 다음 번호를 부여한다. ‘기존 최대 번호’는 삭제·폐기를 포함하여 해당 페이지에서 역대 부여한 번호 중 가장 큰 번호를 뜻한다. 동일 페이지 안에서는 ID를 중복 부여하지 않으며, 삭제·폐기한 ID도 재사용하지 않는다. 폐기·제외·대체가 확정된 항목은 대장 행을 실제로 지우지 않고 결정 상태를 `[삭제 확정]`으로 표시하며, 기존 ID·내용과 처리 이유·관련 결정 기록을 보존한다. 연결된 본문 작업 항목에도 같은 상태를 표시한다. 동일 작업·변경의 내용·상태·순서·문서 버전이 바뀌어도 ID는 유지한다. 하나의 항목을 둘 이상으로 분리하거나 여러 항목을 하나로 통합하기로 확정한 경우, 기존 항목은 본문과 대장에서 `[삭제 확정]`으로 보존하고 현재 작업 및 진행 집계에서 제외한다. 새 항목에는 각각 새 변경 ID를 부여하고 기존 항목과 새 항목 사이의 대체 관계를 양쪽 기록에 연결한다. 다른 협업 작업 페이지의 항목을 참조할 때에는 해당 페이지 링크와 변경 ID를 함께 표기한다.
4. **진행 현황 요약:** 표 위에는 `전체 N건 | 완료 C건 | 진행 중 P건 | 미착수 U건 | 검증 필요 V건 | 완료율 C/N × 100%` 형식의 요약 표를 둔다. ‘보류’ 열은 요약 표에 두지 않는다. 집계 대상은 대장에 등록된 중복 없는 최하위 작업·변경 단위로 하며, 결정 상태가 `[삭제 확정]`이고 그 사유가 제안 폐기 또는 작업 항목의 제외·대체인 항목은 집계에서 제외하여 별도 표시한다. 실제 작업물의 삭제를 수행하는 작업은 `[삭제 확정]`이라는 상태만으로 집계에서 제외하지 않고, 해당 삭제 작업의 진행 상태에 따라 집계한다. ‘전체’는 집계 대상의 총건수, ‘완료’와 ‘미착수’는 각각 작업 진행 상태가 ‘완료’와 ‘미착수’인 건수로 한다. ‘진행 중’은 작업 진행 상태와 별도로, 결정 상태가 `[논의 중]`인 건수와 `[선행 결정 대기]`인 건수를 합한 값으로 한다. ‘검증 필요’는 결정 상태에 `[검증 필요]` 플래그가 붙은 항목의 건수로 하며, 다른 집계와 중복될 수 있다. 결정 상태와 작업 진행 상태를 함께 집계하므로 ‘완료·진행 중·미착수·검증 필요’의 합이 전체와 일치해야 하는 것은 아니다. 완료율은 완료 건수를 전체 건수로 나누어 산출하며, 전체가 0건이면 ‘해당 없음’으로 표시한다. 요약은 작업 건수 기준의 현황이며, 작업량·소요 시간의 비율과 구분한다.

⑥ **변경 이력 표의 형식:** 제2항제5호는 Notion의 표 기능으로 작성하며 기본 열은 ‘버전’, ‘일자’, ‘변경 대상’, ‘변경 내용’, ‘변경 이유’, ‘승인’으로 한다. 변경 이유에는 필요 시 폐기·제외의 범위와 재도입을 경계해야 하는 조건을 명시한다. 변경 이력은 현행 지시를 이해하기 위한 참고 정보이며, 과거 지시를 실행하거나 복원하는 근거로 사용하지 않는다. 단순 오탈자 등 실행 판단에 영향이 없는 수정은 간략히 기록할 수 있다.

⑦ **정합성과 우선순위:** 제3절의 현행 실행 명령, 제4절의 변경 대장 및 제5절의 변경 이력이 상충하면 해당 항목을 임의로 해석하거나 수행하지 않고 상충 사항을 보고한다. 변경 대장이나 변경 이력으로 현행 본문의 승인 범위를 확대·축소하지 않는다. 버전의 부여 및 확정 기준은 제6조에 따른다.

## 제5조(절·항목 및 표기)

① **제목 계층:** 협업 작업 페이지의 제목은 Notion의 페이지 제목으로 작성하며, 본문 주요 절은 ‘제목 1’, 제4조의 작업 항목 `3.1` 등은 ‘제목 2’, 그 하위 작업 항목 `3.1.1` 등은 ‘제목 3’ 기능으로 표시한다. 제목 계층은 페이지 구조를 나타내는 서식이며, 작업 항목 번호는 해당 작업을 식별하는 번호로서 서로 구분한다.

② **목록·표·예시 및 부록:** 사용자가 정보를 읽고 이해하는 방식에 맞춰 다음 각 호에 따라 Notion의 표시 기능을 사용한다.

1. **번호 목록:** 작업의 순서나 선후 관계가 있을 때 사용한다.
2. **글머리표 목록:** 순서 없이 여러 조건이나 사항을 나열할 때 사용한다.
3. **표:** 같은 항목을 기준으로 내용을 비교하거나 상태·진행 현황을 확인할 때 사용한다.
4. **예시:** 규칙만으로 실제 작성 모습을 이해하기 어려울 때 사용한다.
5. **부록:** 반복해서 참고할 양식·예시나 본문에 두면 흐름을 끊는 긴 보충 자료를 둔다.
6. **본문과 상세 설명:** 본문에는 현재 판단에 필요한 내용을 남기고, 상세 설명은 필요한 경우 Notion의 토글 기능으로 접어둘 수 있다.
7. **예시·부록의 작성 원칙:** 예시와 부록은 필요한 경우에만 사용하며, 본문의 규칙을 설명·보완하는 범위에서 작성한다. 예시나 부록에서 새로운 의무를 추가하지 않는다.

제4조제3항의 `(1)`, `(2)` 등 세부 구분은 제목 기능으로 표시하지 않고 일반 텍스트나 목록으로 작성한다.

③ **식별자 표기:** 변경 ID·파일 위치·함수명·식 번호 등 추적에 필요한 식별자는 원문과 일치하도록 기재하며, 제2조제2항의 원문 유지 원칙을 따른다.

④ **표기 일관성:** 동일한 종류의 정보에는 페이지 전체에서 일관된 Notion 표시 형식을 사용한다. 표·목록·제목 계층을 조정하더라도 작업 항목의 식별 번호와 참조 관계가 불명확해지지 않도록 한다.

⑤ **근거 작성:** 협업 작업 페이지에서 근거를 작성·제시할 때에는 [TPL-003 — 근거 제시 규정](https://app.notion.com/p/TPL-003-3f44e2f6c2f181cda573f567cfa51683?pvs=21)(참조 기준 v1.0)을 따른다. 출처·확인 위치, 근거 종류·신뢰도 및 미확인 자료의 표기·취급 등 구체적인 작성 방식은 해당 규칙을 적용한다.

## 제6조(지시 문서의 변경 및 버전 관리)

① **관리 대상의 구분:** 협업 작업 페이지에서 논의한 쟁점·결정·변경과 작업 진행 현황은 작업 기록과 변경 대장으로 추적하며, 기록 관리 절차는 PROC-001 제6조를 따른다. 제4조제2항제5호의 ‘지시 문서 변경 이력’에는 사용자가 페이지의 버전별 주요 변경과 그 이유를 확인할 수 있도록 요약한다. 변경 대장은 개별 작업·변경의 상태와 진행을, 변경 이력은 페이지 자체의 버전별 변화를 보여 주는 기록으로 구분하며, 같은 내용을 전부 중복해서 수록하지 않는다.

② **변경 기록 및 승인 추적:** 변경 관리에서는 다음 각 호를 따른다.

1. 변경 대장의 구성은 제4조제5항에 따르며, 작업 기록과 승인 기록은 기존 ID·위치·링크로 연결한다.
2. 변경 대상이 다른 작업 항목·정의·참조·검증 기준에 영향을 미치면 PROC-001 제7조에 따라 연쇄 영향을 점검한다. 기존 기록의 ID·위치·링크를 활용하여 불필요한 중복 작성을 피한다.
3. 승인되지 않은 변경안과 승인된 실행 항목을 구분하고, 사용자의 승인 및 PROC-001 제4조의 상태 변경 요건을 충족하지 않은 내용을 임의로 확정하지 않는다.

③ **버전 상승 및 수정 수준:** 개별 편집이나 작업 항목의 상태 변경만으로 버전을 자동 상승시키지 않는다. 사용자가 현재 변경의 기록이나 하루 작업의 마무리를 위하여 버전 상승을 요청하는 경우, 사용자와 AI가 수정 수준을 명시적으로 합의한 뒤 다음 각 호의 기준에 따라 한 단계만 상승시킨다.

1. **Major 수정:** 버전 번호의 첫째 자리 정수를 1 증가시키는 수정으로 한다.
2. **Minor 수정:** 버전 번호의 점 뒤 정수를 1 증가시키는 수정으로 한다.
3. **수정 수준의 결정:** 변경의 양·중요도에 관계없이 사용자와 AI의 명시적 합의로 Major 또는 Minor를 정한다. 변경량에 따른 자동 분류나 한 번에 2 이상 증가시키는 변경은 허용하지 않는다.
4. **기록:** 버전 상승 시 변경 대상·내용·이유·일자 및 승인 기록을 제5항의 변경 이력에 반영한다.

버전 상승은 당시의 문서 상태를 식별·보존하기 위한 행위이며, 미결 항목의 확정이나 PROC-001의 컴파일·이관·실행 승인을 의미하지 않는다.

④ **가안 문서와 정식 문서의 구분:** 버전 식별과 단계 승격은 다음 각 호에 따른다.

1. **가안 문서:** 사용자의 요청에 따라 AI가 우선 작성한 초안으로서 `v0.1`부터 시작한다. 이후 수정 버전도 첫째 자리 `0`을 유지하며, 일반적인 버전 상승으로 `v1.0` 이상의 정식 문서가 될 수 없다.
2. **정식 문서:** 사용자의 의견을 반영한 뒤 사용자가 명시적으로 정식 문서로의 승격을 선언한 경우에만 해당 문서를 정식 문서로 취급한다. 승격 시 직전 가안의 버전 번호와 관계없이 `v1.0`을 부여한다(예: `v0.99 → v1.0`). 이 승격은 제3항의 통상적인 Major/Minor 수정과 구분한다.
3. **승격과 실행 승인:** 정식 문서로의 승격은 PROC-001의 논의 종결·컴파일·이관 요건을 대신하지 않으며, 그 자체로 실제 작업 실행을 허용하지 않는다.
4. **이력 보존:** 버전이 변경되거나 문서가 승격될 때에는 이전 버전과 변경·승격 내역을 식별할 수 있도록 보존한다. 미승인 상태의 내용을 승인된 실행 지시로 표시하지 않는다.
5. **번호 해석:** 버전 번호는 첫째 자리와 점 뒤 자리의 정수로 구분해 관리하며, 점 뒤 자릿수를 소수값처럼 해석하지 않는다. Major 수정 시 첫째 자리 정수를 1 증가시키고 기존 Minor 번호는 `0`으로 초기화한다(예: `v1.4 → v2.0`). 가안 문서는 정식 문서 승격 전까지 첫째 자리 `0`을 유지하며, 일반적인 Major 상승을 적용하지 않는다.

⑤ **변경 이력의 작성:** 제4조제2항제5호와 제4조제6항에 따라 Notion의 표 기능으로 작성하며, 기본 열은 ‘버전’, ‘일자’, ‘변경 대상’, ‘변경 내용’, ‘변경 이유’, ‘승인’으로 한다. ‘변경 대상’은 가능한 한 작업 항목 번호 또는 식별자로 연결하고, ‘승인’에는 사용자 승인 기록 또는 확인 가능한 참조를 기재한다. 폐기·삭제의 이유 및 현재 제외 범위는 사용자가 변경 경위와 현재 적용 내용을 이해하는 데 필요할 때 명시한다.

⑥ **실행 명령과의 분리:** 변경 이력은 현행 지시를 이해하기 위한 참고 정보이며, 과거안을 복원하거나 실행할 권한을 부여하지 않는다. 현행 지시와 변경 이력 사이에 해소되지 않은 상충이 발견되면 PROC-001과 GOV-001의 중단·보고 원칙에 따라 처리한다.

## 제7조(문장 작성 방식)

협업 작업 페이지에서 AI는 사용자가 내용을 쉽게 이해하고 판단할 수 있도록 다음 각 호에 따라 서술한다.

1. 명령형을 일률적으로 쓰지 않고, 내용에 맞는 자연스러운 설명형 문장으로 쓴다.
2. 핵심을 먼저 쓰고, 이유와 세부 설명은 뒤에 둔다.
3. 한 문장에는 하나의 판단이나 요구만 담는다.
4. 무엇을, 왜 하는지, 어떤 결과를 기대하는지 구체적으로 쓴다.
5. '적절히', '필요에 따라'처럼 해석이 갈리는 표현을 쓸 때는 그 기준을 함께 쓴다.
6. 확인된 사실과 AI의 해석·추측·제안이 문장에서 구분되도록 쓰고, 확인되지 않은 내용은 단정적으로 쓰지 않는다.
7. 사용자가 결정할 내용이 있으면 결정할 내용, 선택지, AI의 권고와 그 이유를 쓴다.

## 제8조(전달 대상·내용 및 매체)

① **전달 대상:** 협업 작업 페이지의 전달 대상은 사용자로 한다.

② **전달 내용:** 사용자가 작업 내용, 결정 상태, 논의 경과, 변경 대장, 문서 버전 및 남은 작업을 확인할 수 있도록 하나의 협업 작업 페이지에 정리한다. 관련 원본·참조 자료와 상세 기록은 필요한 위치에 연결한다.

③ **전달 매체:** 전달 매체는 Notion 페이지로 한다. 사용자가 해당 페이지와 연결된 자료에 접근하여 내용을 확인할 수 있도록 구성한다.

④ **전달과 실행 승인의 구분:** 협업 작업 페이지의 작성·승인·전달은 실제 파일 수정이나 작업 실행의 자동 승인을 뜻하지 않는다.

## 제9조(양식 점검 및 예외)

① 협업 작업 페이지를 전달하기 전에 페이지 형식, 머리말, 필수 절, 식별자, 산출물 명세, 연결 자료의 접근 가능성 및 사용자가 내용을 이해할 수 있는지를 확인한다.

② 형식상의 편의를 이유로 GOV-001 및 PROC-001의 승인·검증·중단 요건을 완화하지 않는다.

③ 특수한 형식이 필요한 경우 예외의 필요성·적용 범위·호환성·승인 여부를 명시하고 별도로 논의한다.

- 논의 경과와 미승인·미결·검증 필요 사항도 상태를 구분하여 기록할 수 있다. 필요하면 Notion 토글·페이지 멘션·링크로 상세 기록을 연결한다.

- 전달 대상은 사용자이고 전달 매체는 Notion 페이지이다. 페이지의 작성·승인·전달이나 정식 문서 승격만으로 실제 작업의 실행이 승인된 것으로 보지 않는다.
- 최종 실행 지시서의 구성·출력 양식은 TPL-002에서 다루며, 이 협업 페이지 양식과 구분한다.

## 부록 B. 설계 쟁점 및 처리 결과

- **TPL-Q01 [확정]:** 산출물 파일명은 대상·용도·필요한 버전 등을 식별할 수 있으면 되며, 고정된 파일명 규칙을 일률적으로 요구하지 않는 것으로 정하였다. 제2조제5항에 반영하였다. 협업 작업 페이지의 이름은 산출물 파일명과 구분하여 제2조제4항을 따른다.
- **TPL-Q02 [확정]:** TPL-001의 적용 대상을 최종 실행 지시서에서 Notion 협업 작업 페이지로 변경함에 따라, 기존 ‘표준 절 9개’의 제목·순서 및 통합 여부에 관한 쟁점은 종료한다. 협업 작업 페이지의 본문은 제4조제2항의 6개 절 구성을 기준으로 하며, 제6절 ‘실행 제외 항목’은 선택 항목으로 둔다. 최종 실행 지시서의 구성은 TPL-002에서 다룬다.
- **TPL-Q03 [확정]:** 제3조제2항의 문서 버전·문서 상태·작업 목적·작업 범위는 필수 항목으로, 제3조제3항의 작성 기준일·문서 식별자는 선택 항목으로 정하고 해당 조항에 명시하였다.
- **TPL-Q04 [확정]:** TPL-001의 적용 대상을 Notion 협업 작업 페이지로 변경하고, 제2조제3항 및 제8조제3항에 따라 작성·전달 매체를 Notion 페이지로 정하였다. 원본·참조 자료와 상세 기록은 제8조제2·3항에 따라 페이지에서 연결하고 사용자가 접근할 수 있도록 한다. 최종 Markdown(`.md`) 실행 지시서의 출력·전달 형식은 TPL-002에서 다룬다.
- **TPL-Q05 [확정]:** 제5조제2항에 사용자가 정보를 읽고 이해하는 방식을 기준으로 번호 목록·글머리표·표·예시·부록의 사용 기준을 명시하였다. 순서·선후 관계는 번호 목록, 순서 없는 나열은 글머리표, 비교·상태·진행 현황은 표, 작성 모습의 이해를 돕는 내용은 예시, 반복 참조 양식이나 긴 보충 자료는 부록으로 구분하였다. 본문에는 현재 판단에 필요한 내용을 남기고 상세 설명에는 Notion 토글을 사용할 수 있도록 하며, 예시·부록에서 새로운 의무를 추가하지 않는 원칙을 반영하였다.
- **TPL-Q06 [확정]:** 제4조제1항·제2항제3호·제4항 후단 및 제6조제1항을 사용자와 공유하는 협업 작업 페이지의 문구로 수정하고, 제4조제3항의 마지막 하위 절 명칭을 ‘공통 작업·확인·기록 조건’으로 맞추었다. 부록 A도 현행 TPL-001에 맞춘 Notion 협업 작업 페이지 표준 양식으로 교체하여 논의·미결 기록, 변경 대장 및 진행 현황을 포함하였다. 최종 실행 지시서의 양식은 TPL-002의 영역으로 구분하였다.
- **TPL-Q07 [확정]:** 제6조제5항을 Notion의 표 기능으로 작성하도록 수정하고, 기본 열을 제4조제6항과 동일하게 명시하였다. 협업 페이지 변경 이력에 대한 Markdown 표 작성 요구를 없애고 Notion 표 기준으로 통일하였다.
- **TPL-Q08 [확정]:** 부록 A의 오래된 ‘최초 버전 번호와 상승 폭은 추가 논의 대상’이라는 안내를 삭제하고, 버전 부여·상승·정식 문서 승격은 제6조를 따르도록 수정하였다. 본문에 정한 버전 규칙과 부록의 안내를 일치시켰으며, 해당 정합화 당시에는 검토 초안의 지위를 유지하였다. 이후 정식 문서 승격 내역은 부록 C에 기록하였다.
- **TPL-Q09 [확정]:** PROC-001 제8조제1항의 필수 실행 지시 사항은 TPL-002와 관련된 내용이므로, 제4조제2항에서 ‘세부 항목의 수와 깊이는’ 이후의 문장 전체를 삭제하였다. 협업 작업 페이지의 표준 절 구성만 남기고, 실행 지시서 요건 및 존재하지 않는 ‘부록 ○ 대응표’ 참조를 제거하였다.
- **TPL-Q10 [확정]:** ‘기존 최대 번호’를 삭제·폐기를 포함한 역대 부여 번호의 최댓값으로 정의하고, 새 ID는 그 다음 번호로 부여하며 기존 ID는 재사용하지 않도록 하였다. 폐기·제외·대체된 항목은 행을 지우지 않고 기존 ID·내용과 처리 이유·관련 결정 기록을 보존한다. 해당 항목의 상태 표시는 Q11의 후속 결정에 따라 별도의 `[삭제]` 대신 기존 결정 상태인 `[삭제 확정]`을 사용하도록 통일하였다.
- **TPL-Q11 [확정]:** 항목의 폐기·제외·분리·통합에 따른 대체는 기존 결정 상태인 `[삭제 확정]`을 본문과 변경 대장에 함께 표시하는 방식으로 정하였다. 분리·통합된 기존 항목은 실제로 지우지 않고 기록을 보존하되 현재 작업과 진행 집계에서 제외한다. 새 항목에는 새 변경 ID를 부여하고 양쪽 기록에 대체 관계를 연결한다. 실제 작업물의 삭제를 수행하는 작업과 기록 자체의 제외·대체는 대상·이유로 구분하며, 실제 삭제 작업은 `[삭제 확정]` 상태만으로 집계에서 제외하지 않는다. 제4조제4·5항과 부록 A에 반영하였다.
- **TPL-Q12 [제기]:** 상위 작업 항목의 상태. 제4조제4항은 모든 계층의 작업 항목에 상태를 표시하도록 하나, 하위 항목이 모두 확정된 경우 상위 항목의 상태를 정하지 않는다. 사용자는 ‘하위 항목이 모두 확정되면 상위 항목도 확정으로 본다’는 규정의 추가가 필요하다고 판단하였다(도현, 2026년 10월 9일). 발견 경위: 작업공간_TPL002수정 3.1.
- **TPL-Q13 [제기]:** 진행 현황 요약표의 집계 기준. 제4조제5항제4호의 ‘완료·미착수’는 작업 진행 상태를, ‘진행 중’은 결정 상태를 세며 [확정]·[제기]는 세지 않는다. PROC-001 논의 단계에서는 모든 항목의 작업 진행 상태가 미착수로 남아 확정 건수 등 진척이 요약표에 드러나지 않는다. 개선안 후보는 결정 기준(제기·논의 중·선행 결정 대기·확정·삭제 확정)과 반영 기준(미착수·진행 중·완료·보류)을 나눈 두 줄 요약표이다(AI 제안). 사용자는 추후 수정이 필요하다고 판단하였다(도현, 2026년 10월 9일). 발견 경위: 작업공간_TPL002수정 제4절.
- **TPL-Q14 [제기]:** 제목 변경 기록의 불일치. 부록 C 정식 v1.0 이력은 제목을 ‘TPL-001 — 협업 작성 환경 지시 규정’으로 변경했다고 적지만, 실제 페이지 제목과 머리말은 ‘협업 작성 환경 지시 규칙’이다. 규칙 문서 간 ‘규칙’·‘규정’ 명칭 혼용(TPL-003 ‘근거 제시 규정’ 등)과 함께 검토한다. 발견 경위: 작업공간_TPL002수정 제6절(2026년 10월 9일).
- **TPL-Q15 [제기]:** 협업 작업 페이지의 문서 버전 삭제 여부. 제2조제4항의 페이지 이름 버전, 부록 A 머리말 표의 문서 버전·문서 상태, 제6조의 버전 관리와 가안·정식 구분이 협업 페이지에 필요한지 검토한다. 계기: TPL-002 수정 작업에서 최종 지시서의 가안 단계와 버전 표기가 불필요하다고 판단하면서, 협업 페이지의 버전도 필요한지 따져 보기로 함(도현, 2026년 10월 9일). 발견 경위: 작업공간_TPL002수정 3.4.1.
    - 사용자 의견(도현, 2026년 10월 9일): 실행 지시 문서와 협업 작업 페이지는 고쳐 다시 쓰기보다 매번 새로 작성하는 편이 나을 것 같다. 페이지와 실행 지시 문서 모두 버전 없이 작성 기준일을 붙여 구별하도록 하자.
- **TPL-Q16 [제기]:** 최종 `.md` 문서의 명칭 통일. 제1조제4항 등에서 쓰는 ‘실행 지시서’를 ‘실행 지시 문서’로 통일한다. 근거: GOV-001 제1조제4항은 `.md` 등 파일 형식의 기록물을 ‘문서’로, 제1조의2제1항제8호는 ‘지시 문서’를 정의한다. TPL-002는 같은 명칭으로 통일하기로 함(도현, 2026년 10월 9일). 발견 경위: 작업공간_TPL002수정 3.4.3.
- **TPL-Q17 [제기]:** 부록 B 쟁점 ID 형식의 변경. 현행 `TPL-Q01`~`TPL-Q17`을 문서 식별자를 포함한 `TPL-001-Q01`~`TPL-001-Q17` 형식으로 바꾼다. 이 쟁점은 변경 후 `TPL-001-Q17`이 된다. 계기: TPL-002 부록 B의 쟁점 ID를 `TPL-002-Q01` 형식으로 바꾸기로 하면서(도현, 2026년 10월 9일) 두 문서의 ID 형식을 맞추기 위함. 변경 시 GOV-001 제5조제2항에 따라 종전 ID와 새 ID의 대응을 개정 이력에 남기고, 작업공간_TPL002수정 등 다른 페이지의 `TPL-Q` 참조도 추적한다. 발견 경위: 작업공간_TPL002수정 3.5.

## 부록 C. 제정·개정 및 승격 이력

- **초안 v0.1 — 2026-10-08:** PROC-001에서 생성하는 최종 지시 문서에 범위를 한정하여 출력 형식·절 구성·문체·전달 규격의 최초 검토안 작성. 승인 전 문서임.
- **초안 v0.2 — 2026-10-08 (Minor: v0.1 → v0.2):** 제1조를 Notion 협업 작업 페이지의 목적·적용 범위·협업 작성 환경·타 규정과의 관계로 개정하여, PROC-001의 절차 및 TPL-002의 최종 Markdown(`.md`) 실행 지시서 양식과 역할을 구분함. 제2조를 사용자가 읽고 확인하기 쉬운 Notion 페이지 형식으로 개정하고, 페이지명 규칙을 `작업공간_작업목표_버전`으로 변경함. 한국어 작성·기술 용어 병기·원문 유지 규칙은 유지하고, Notion 표시 기능을 활용하도록 정리함. 변경 이유: 협업 작업 페이지와 최종 실행 지시서의 양식을 분리하고 오늘의 수정 상태를 기록하기 위함. 승인 기록: 사용자의 당일 마무리 및 부록 C 이력 추가 요청과 ‘Minor: v0.1 → v0.2’ 선택에 따름. 이번 버전 상승은 정식 문서 승격이나 실행 승인을 의미하지 않음. 제3조 이하 및 부록의 내용 정합성은 후속 검토 대상으로 남김.
- **정식 v1.0 — 2026년 10월 9일 (승격: 초안 v0.2 → 정식 v1.0):** 사용자의 명시적 승격 요청에 따라 TPL-001을 정식 문서로 승격하고, 제목을 ‘TPL-001 — 협업 작성 환경 지시 규정’으로 변경하였다. 사용자와 Notion에서 공동 작성·논의하는 작업 페이지를 기준으로 머리말, 본문 구성, 제목·목록·표·예시·부록의 사용, 문장 작성 방식, 전달·점검 기준을 정리하였다. 변경 대장과 진행 현황 요약, 변경 ID의 부여·보존, 분리·통합 시 기존 항목의 삭제 확정 표시 및 집계 제외, 가안·정식 문서의 버전 관리를 반영하였다. 근거 작성은 TPL-003을 따르도록 연결하고, 부록 A·D를 현행 규정에 맞는 Notion 양식으로 정리하였다. 부록 B의 TPL-Q01~Q11에 사용자와 합의한 처리 결과를 기록하였다. 변경 이유: 검토·정리한 협업 작성 환경의 규정을 정식 기준으로 사용하고 문서의 역할을 제목에 명확히 드러내기 위함. 승인 기록: 사용자의 정식 문서 승격 및 제목 변경 요청에 따름. 이번 승격은 제6조제4항에 따른 단계 승격이며 통상적인 Major·Minor 상승과 구분하고, 개별 작업의 실행 승인을 의미하지 않는다. 기존 초안 v0.1·v0.2의 이력은 보존한다.
